# Configuration

Veksel product configuration is owned by `data/config.toml`. Environment
variables do not override product settings. The only bootstrap choice is the
`--data-dir` process flag, which tells Veksel where to find the managed file and
the rest of its durable state.

On first launch Veksel writes a documented default TOML file with mode `0600`.
TOML comments and key ordering are preserved when an administrator changes an
individual value through the API or administration interface.

The checked-in [default configuration](configuration-default.toml) is the exact
document generated by `config.DefaultAt("./data")`. A test compares it
byte-for-byte with the current code, so it is the authoritative reference for
every managed key and default. The focused tables below explain settings whose
relationships or operational behavior need more context, and the closing
"Remaining settings reference" lists every other key with its default. The live administration API remains authoritative for
normal/advanced placement, sensitivity, desired/effective values, and apply
state in a running build.

## First start

Start Veksel with a private empty data directory and visit `/app/setup`. The
first-claim page creates the initial system owner only while the user store is
empty; complete it before exposing the listener to an untrusted network. The
equivalent lifecycle API is `GET /api/v1/setup` followed by a CSRF-protected
`POST /api/v1/setup`. Existing users without a system owner are deliberately
treated as a blocked store rather than upgraded implicitly.

## Administration API

| Method and path | Purpose |
|---|---|
| `GET /api/v1/admin/config` | Return values, schema metadata, and the current revision |
| `GET /api/v1/admin/config/history` | Return newest-first retained revision activations and redacted structured diffs |
| `POST /api/v1/admin/config/validate` | Return a validated candidate and dependency-aware plan without publishing it |
| `PATCH /api/v1/admin/config` | Atomically apply and return the exact plan prepared under the commit lock |
| `POST /api/v1/admin/config/history/{revision}/validate` | Preview the exact plan for restoring a retained revision |
| `POST /api/v1/admin/config/history/{revision}/restore` | Restore a selected retained revision using optimistic concurrency |
| `POST /api/v1/admin/config/recover` | Restore the previous valid document |

These endpoints accept a browser session or an administrator's `X-API-Key`
(see [authorization](authorization.md#api-key-capabilities)). `/admin`
redirects to the unified administration workspace.

Every write includes the revision returned by the preceding read. A stale
revision returns `409 Conflict`, preventing two administrators from silently
overwriting each other. Writes use a temporary file, `fsync`, atomic rename,
and directory `fsync`. The previous valid document is retained as
`config.previous.toml`.

The API schema identifies normal and advanced settings and sensitive values.
The administration UI is generated from the same schema. Each setting also
reports its desired and effective value and an explicit apply state.
Sensitive values are redacted in both columns.

### Live apply

Every setting applies live; no configuration change requires a restart. Each
runtime component that reads a setting registers a live applier for it with
the configuration service. When a committed change touches one of its keys,
the owner receives the complete new snapshot and swaps its state atomically:
work already in progress (an SMTP session, a queued delivery attempt, a
running search build, an in-flight webhook request) finishes on the values it
started with, and subsequent work uses the new ones. Configuration is never
mutated underneath an active protocol request. Listener changes rebind
without dropping established sessions, and a listener that cannot bind keeps
the running one.

Each affected key moves through these apply states:

| State | Meaning |
|---|---|
| `applying` | The owner is applying the committed value |
| `effective` | The owner accepted the value; desired and effective agree |
| `failed` | The owner rejected the value; a bounded error and the last effective value are retained |

A failed key keeps serving its last effective value until a later edit
succeeds, and a later edit does not inherit stale failure evidence from an
older desired value. A test starts the real server and fails if any setting
lacks a live applier.

`system_engine` is the one exception and the only setting whose schema still
reports `restart_required`. A new engine would open an empty system store, so
the configuration API refuses to change it while Veksel runs: stop the server,
convert the data with the offline `veksel-store-migrate` tool, then edit
`system_engine` in `config.toml`. Restarting the server
remains available from Operations, but no setting depends on it.

Runtime input inventory is deliberately small. `--data-dir` is the sole
bootstrap locator. Build metadata and compile-time protocol gates are immutable
build facts. Test subprocess variables and development-watcher controls are not
server behavior. Production packages do not read behavioral environment
variables, secrets, or listener overrides; credentials and certificate private
keys remain in their dedicated stores and are redacted from configuration
responses, revision diffs, and logs.

## Revision history

Every initial load, successful API/UI patch, external-file reload, recovery,
and selected restore records an immutable activation event under
`data/config-history`. Events include the active and parent revisions, UTC
time, bounded actor/source/reason fields, and a structured list of changed
keys. Sensitive before/after values are replaced by `[redacted]` in event
metadata. Full snapshots remain private recovery material with mode `0600` and
are never returned by the history API.

The newest 50 activation events are retained. Content-addressed TOML snapshots
shared by more than one event—for example when restoring an older revision—are
kept once and removed only after no retained event references them. Restoring
a selected revision creates a new activation event instead of rewriting
history. Both patch and restore requests must name the currently active
revision and return `409 Conflict` when another administrator won the race.
An un-reloaded external edit is also a conflict, so a managed patch cannot
silently absorb or overwrite bytes that differ from its base revision.

## Change plans

Validation and commit use one planner over the complete candidate document.
The plan contains its base and proposed content revisions, deterministic
per-setting before/after/effective values, sensitivity and restart impact,
live-apply keys, and every affected dependency group. Current groups cover the
shared HTTP surface, SMTP, IMAP, POP3, queue/retry limits, routing, account
storage placement, quota pressure, health alerts, folder history, cache, search,
greylisting, and ACME. Cross-setting
invariants—such as per-destination versus total queue concurrency, retry
bounds, listener syntax, and primary account-root references—are checked
against the complete candidate rather than individual form fields.

`PATCH` returns the exact plan it committed; it does not regenerate a similar
plan after publishing. Selected restore follows the same contract. API and UI
clients can therefore preview one coherent multi-setting operation and verify
the committed base/proposed revisions without reproducing server validation.

The administration workspace exposes the same contract directly. Its setting
finder searches labels, stable keys, categories, and descriptions across every
normal, advanced, and protocol-owned page, then opens and focuses the owning
control. Edits are staged across administration navigation and reviewed as one
server-validated plan before apply. Non-sensitive staged values persist in the
signed-in browser UI state; secrets are intentionally memory-only and are
removed from any previously persisted state. The revision-history modal shows
actor, reason, source, time, redacted changed keys, and validates a selected
restore before enabling the restore action.

## Storage and consistency settings

| TOML key | Default | Meaning |
|---|---:|---|
| `system_engine` | `pebble` | Backend for global metadata and the system queue (`pebble` or `badger`) |
| `default_account_engine` | `pebble` | Backend assigned to newly discovered accounts |
| `change_history_retention_days` | `90` | Age limit for incremental change records |
| `change_history_max_entries` | `1000000` | Per-account change-entry limit |
| `account_idle_close_seconds` | `300` | Close an unused account backend after this interval; `0` disables closing |
| `storage_encryption_default` | `false` | Encrypt newly created accounts at rest; applies live and never touches existing accounts |
| `search_index_encrypted_accounts` | `false` | Also keep the on-disk full-text index, which holds plaintext terms, for accounts encrypted at rest |
| `quota_warning_percent` | `80` | Highest limited-resource usage where an account enters warning state |
| `quota_critical_percent` | `95` | Highest limited-resource usage where an account enters critical state |
| `folder_cache_enabled` | `true` | Enable the transparent authorized read cache |
| `folder_cache_ttl_seconds` | `30` | Maximum lifetime of a cached read |
| `folder_cache_max_entries` | `4096` | Global cache entry ceiling |
| `folder_cache_max_bytes` | `67108864` | Approximate cache memory ceiling |

An account whose backend was closed for idleness is transparently reopened on
its next operation. Active leases and account conversion fence idle closing.
The read cache is bounded by both entries and bytes, returns defensive copies,
and invalidates affected folder/item scopes after successful mutations.
Delegated and shared reads deliberately bypass it so an RBAC change cannot
leave another user's data in an authorization-insensitive cache entry.
Quota thresholds apply live and are validated together: warning must be from 1
through 99, critical from 2 through 100, and warning must remain lower than
critical. The higher percentage of the configured item or logical-byte limit
drives account pressure; an account with neither limit remains `unlimited`.

## Retention and legal hold settings

| TOML key | Default | Meaning |
|---|---:|---|
| `retention_enabled` | `true` | Run the background job that applies retention policies |
| `retention_job_interval` | `6h` | Time between retention passes, a duration from `15m` to `168h` |
| `retention_min_days` | `30` | Shortest delete age, in days, a domain administrator may give a retention policy |
| `legal_hold_domain_admins` | `false` | Let domain administrators place and release legal holds and run eDiscovery exports for their domains |

All four apply live. Retention policies and legal holds themselves are
records, not settings: they are managed under **Administration → Compliance**
or through `/api/v1/admin/compliance` and are kept in the system store, so
they are included in installation backups.

A retention policy deletes, or moves to the account's Archive folder, mail
older than a number of days by its received (internal) date. It applies to the
whole installation, a domain (accounts whose primary identity is in it), or one
account, and to every mail folder, to one special folder (Inbox, Sent, Archive,
Trash, Junk), or to folders whose path matches a pattern (`Clients/*`,
`Projects/**` for a folder and all its descendants, case-insensitive). The most
specific policy wins: account over domain over installation, then a special
folder over a path pattern over all folders; between equally specific
policies, the one keeping mail longest wins. Only system administrators set
installation policies; domain administrators set domain and account policies
for their domains, and their delete policies must keep mail at least
`retention_min_days`.

The job walks accounts in login order. After each account it persists the
last completed login, so a restart resumes where it stopped, and an account
interrupted mid-way is rescanned (already processed messages no longer match).
A pass performs at most 5,000 deletions or moves, paced a few milliseconds
apart, and the next pass continues from the cursor. Every pass writes a
`retention.run` audit entry with its counts and increments the
`veksel_retention_*` counters. Accounts under legal hold are never pruned.

A legal hold on an account or a domain (every account whose primary identity
is in it; an alias there is not enough) has a reason or case ID and an
optional end date, after which it lapses on its own. While it is active, deletion is preserved at the single FolderSpace layer
that every protocol uses: an IMAP EXPUNGE, JMAP destroy, EWS or ActiveSync
delete, POP3 DELE, DAV DELETE, web deletion, trash empty, or folder purge
moves the items into a hidden per-type held-deleted folder instead of
destroying them. The account and its clients see the item disappear (their
change feeds report it destroyed); compliance views and eDiscovery exports
still find it with its original folder and deletion time. Retention deletions
and compliance deletions are refused outright, item history is not pruned, and
deleting the account is refused with `409 Conflict`. Moving, trashing, and
restoring keep working. When the hold is released or expires, the next
retention pass destroys the items the user deleted while held. Holds are not
shown to the account's user; folder properties show only the effective
retention policy.

Encryption at rest is per account. `storage_encryption_default` only decides
how new accounts are created; enabling it needs the installation key ring,
which every normal start loads. Encrypting, decrypting, or re-keying an
existing account is an explicit administrator conversion with progress,
verification, and a retained rollback generation, not a setting
([Storage](storage.md#encryption-at-rest)). Turning
`search_index_encrypted_accounts` off deletes the plaintext indexes of
encrypted accounts on the next maintenance pass; turning it on builds them.

## Health and alert settings

| TOML key | Default | Meaning |
|---|---:|---|
| `alert_evaluation_seconds` | `15` | Runtime-health reconciliation cadence |
| `alert_queue_warning_minutes` | `15` | Oldest queued item age that opens a warning |
| `alert_queue_critical_minutes` | `60` | Oldest queued item age that escalates to critical |
| `alert_webhook_warning_minutes` | `5` | Oldest pending webhook age that opens a warning |
| `alert_webhook_critical_minutes` | `30` | Oldest pending webhook age that escalates to critical |
| `alert_storage_warning_free_percent` | `15` | Available filesystem percentage at or below which to warn |
| `alert_storage_critical_free_percent` | `5` | Available filesystem percentage at or below which to escalate |
| `alert_certificate_warning_days` | `30` | Remaining lifetime that opens a certificate warning |
| `alert_certificate_critical_days` | `7` | Remaining lifetime that escalates a certificate alert |
| `alert_notifications_enabled` | `true` | Publish alert transitions to administrators and deliver them through the alert channels below |

Queue and webhook warning ages must remain below their critical ages. Storage
critical free percentage must remain below its warning percentage. Certificate
critical days must remain below certificate warning days. These settings apply
live as one dependency group; alert records remain durable when notifications
are off. Capacity collection uses cached filesystem metadata only: it never
walks account directories or item data, and configured paths on one device are
reported as one component. Expired evidence refreshes asynchronously and
coalesces concurrent callers, so a slow or unavailable mount does not block
Health, readiness, startup, or administration requests. The last successful
measurements and collection time remain visible while a delayed refresh is
marked stale. Kernel probes cover the directly built Linux, Darwin, FreeBSD,
OpenBSD, and NetBSD targets; other platforms report unsupported collection as
explicit health evidence instead of fabricated capacity.

## Scheduled backup settings

| TOML key | Default | Meaning |
|---|---:|---|
| `backup_schedule` | `off` | `off`, `daily`, `weekly`, `HH:MM` (daily), or `DAY HH:MM` (weekly, for example `sun 03:00`), in server local time; the shorthands run at 03:00, weekly on Sunday |
| `backup_directory` | `backups` | Destination of scheduled archives; relative paths are inside the data directory |
| `backup_age_recipients` | `[]` | age public keys (`age1...`) or OpenSSH `ssh-ed25519`/`ssh-rsa` public keys that archives are encrypted to; empty stores them unencrypted |
| `backup_retention_daily` | `7` | Keep the newest archive of each of this many most recent days |
| `backup_retention_weekly` | `4` | Keep the newest archive of each of this many most recent ISO weeks |

These settings apply live as one dependency group. Each run uses the online
installation backup, writes `veksel-scheduled-<UTC time>.tar` or `.tar.age`
atomically, verifies the archive stream with the restore drill, and reads the
stored file back to confirm its digest. The durable schedule state records the
last attempt, result, and next run, so a slot missed while the server was down
runs once after startup; changing the schedule takes effect from the change
without catching up earlier slots. Retention needs at least one daily or weekly
archive, always keeps the newest, and deletes only archives the scheduler
recorded writing whose name and size still match. A failed run and a missing
successful run for longer than one schedule period plus six hours raise the
`scheduled-backup` operational alert. Recipient keys are public: the server can
encrypt but not decrypt, and a private key entered by mistake is rejected
without being echoed. [Deployment](deployment.md#scheduled-backups) covers
destinations and encrypted restore.


### Alert delivery channels

| TOML key | Default | Meaning |
|---|---:|---|
| `alert_email_recipients` | `[]` | Administrator addresses (plain `user@domain`, at most 20) that receive alert mail |
| `alert_notify_url` | empty | HTTP(S) URL that receives a JSON push per notification; empty disables push. Redacted like the token, since push URLs often carry a credential |
| `alert_notify_token` | empty | Optional bearer token sent as `Authorization: Bearer …`; redacted everywhere |
| `alert_min_interval_minutes` | `30` | Minimum minutes between notifications for one alert; `0` disables the limit |
| `alert_digest` | `off` | `off` sends each change immediately; `daily` batches changes into one digest every 24 hours |
| `quota_warning_emails_enabled` | `true` | Mail users when usage crosses the quota warning, critical, or 100% threshold |

Each alert transition (opened, escalated, reopened, resolved) is marked
pending on the alert record in the same write that records it, and a notifier
delivers it after every health evaluation, so a restart neither loses nor
repeats a notification. Channels:

- **Email**: one message per recipient, admitted to the outbound queue from
  `postmaster@` the system mail domain (the domain used for DSNs and reports)
  and DKIM-signed at admission. It needs an enabled hosted domain.
- **Webhooks**: existing webhook subscriptions receive `health.alert.opened`,
  `health.alert.escalated`, `health.alert.reopened`, `health.alert.resolved`,
  `health.alert.digest` and `health.alert.test` events with the usual HMAC
  signature and retries. Subscribing is the opt-in.
- **HTTP push**: a `POST` of `application/json`:
  `{"source":"veksel","event":"health.alert.opened","title":"…","message":"…","priority":5,"severity":"critical","timestamp":"…","data":{…}}`.
  `title`, `message` and `priority` (5 critical, 4 warning, 3 info/resolved)
  match Gotify's message API (`https://gotify.example/message` with the
  application token as `alert_notify_token`); other receivers can use `event`,
  `severity` and the alert fields in `data`. Any 2xx response is success.

The push URL and webhook subscriptions may not resolve to loopback, private,
link-local, carrier-grade NAT, or reserved addresses unless
`outbound_http_allow_private_networks` is on (see
[Outbound HTTP endpoints](#outbound-http-endpoints)).

Silenced alerts are not delivered. When an alert flaps back to the state last
notified, the change is coalesced instead of sent; inside the re-notify
interval further changes wait until it elapses, except an escalation of an
active alert, which is sent at once. A resolution of an alert that was never
announced stays quiet. When every channel fails, delivery retries with
exponential backoff (1 minute up to 1 hour, 8 attempts); the outcome, last
error and suppressed count are kept on the alert record. In `daily` digest
mode the first evaluation starts the schedule and pending changes are sent
together every 24 hours. Turning `alert_notifications_enabled` off clears
pending transitions without sending them, so re-enabling does not replay old
changes. Health → Notifications shows each channel and its latest delivery
and sends a test notification.

Quota warnings reuse `quota_warning_percent` and `quota_critical_percent` plus
100%. A metadata-only scan every 10 minutes checks enabled accounts with a
storage or item limit; a user is mailed once each time usage rises across a
threshold, and the remembered level drops with usage so a later crossing warns
again. Accounts at or above 100% raise one `Account quotas` health alert that
resolves when none remain.
## Protocol and queue settings

Listener enablement, addresses, TLS variants, assigned certificates,
authentication mechanisms, limits, routing policy, and ACME are top-level TOML
settings exposed by the same API/UI schema. Important queue controls are:

| TOML key | Default | Meaning |
|---|---:|---|
| `smtp_server_name` | empty (machine host name) | Public FQDN used for EHLO; first-run setup can set it |
| `smtp_public_address` | empty | Public egress IP (set when behind NAT); enables FCrDNS verification in DNS guidance and startup warnings. No network probe is made |
| `smtp_max_received_headers` | `50` | Reject a message that already carries more `Received:` fields with `554 5.4.6 Too many hops` (probable mail loop); 1–1000 |
| `smtp_submission_received_privacy` | `false` | Leave the client IP address and reverse DNS name out of the `Received:` field added to authenticated submissions |
| `queue_max_size` | `10000` | Maximum retained queue records |
| `queue_workers` | `4` | Concurrent delivery workers |
| `queue_max_age_hours` | `120` | Temporary failures retry until this age, then bounce |
| `queue_retry_initial_seconds` | `60` | Initial retry delay |
| `queue_retry_max_seconds` | `14400` | Retry backoff ceiling |
| `imap_max_literal_size` | `52428800` | Maximum bytes in one APPEND literal or complete atomic MULTIAPPEND command |
| `imap_require_tls_auth` | `true` | Refuse LOGIN and plaintext SASL (PLAIN, LOGIN, XOAUTH2) until STARTTLS or implicit TLS is active; cleartext sessions advertise `LOGINDISABLED` and receive `NO [PRIVACYREQUIRED]` |
| `pop3_require_tls_auth` | `true` | Refuse POP3 password authentication until STLS or implicit TLS is active |
| `managesieve_require_tls_auth` | `true` | Refuse ManageSieve password authentication until STARTTLS or implicit TLS is active |
| `mail_max_connections_per_ip` | `200` | Maximum concurrent SMTP, IMAP, or POP3 connections from one client IP on each listener; `0` disables the cap. Size it for every user behind a shared office or NAT address (mail clients keep several connections each) |
| `mail_connection_limit_exempt` | `[]` | IP addresses or CIDR prefixes (for example a webmail or sync gateway) that bypass mail connection limits |
| `mail_proxy_protocol` | `[]` | Mail listeners that accept HAProxy PROXY protocol v1/v2 headers: `smtp`, `imap`, `pop3`, or `managesieve` for all of a protocol's listeners, or one of `smtp-relay`, `submission`, `smtps`, `imap-starttls`, `imaps`, `pop3-starttls`, `pop3s`, `managesieve-starttls`, `managesieve-tls` |
| `mail_proxy_protocol_trusted` | `[]` | IP addresses or CIDR prefixes of the load balancers allowed to send PROXY headers; required when `mail_proxy_protocol` is set |

Every message accepted over SMTP or submission (DATA or BDAT) gets one
`Received:` trace field (RFC 5321 section 4.4) on top, before spam scoring,
delivery, queue admission, and DKIM signing:

```
Received: from client.example.org (mail.example.org [192.0.2.10])
	by mx.example.com (Veksel) with ESMTPS id smtp-transaction-1761170000000000000-7
	(using TLSv1.3 with cipher TLS_AES_128_GCM_SHA256)
	for <bob@example.com>; Wed, 22 Oct 2026 12:00:00 +0000
```

The `from` part is the HELO/EHLO name, the reverse DNS name found by the HELO
check (omitted when that check is off or found none; no extra lookup is made),
and the effective client address (the PROXY-relayed one behind a load
balancer; IPv6 as `[IPv6:...]`). The protocol is `SMTP`, `ESMTP`, `ESMTPS`,
`ESMTPA`, or `ESMTPSA` (RFC 3848), the id is the transaction id used by the
message trace, and `for` names the recipient only when there is one. With
`smtp_submission_received_privacy = true` an authenticated submission keeps
the server name, protocol, id, and date but not the client address or
reverse DNS name. Existing `Received:` fields keep their order and folding in
delivered, relayed, forwarded, and redirected copies. Both settings apply
live to the next transaction.

Mail connection admission is per client IP: besides the concurrent cap, a
flood guard admits a burst of 300 new connections and 10 per second after
that. A refused client receives `* BYE [UNAVAILABLE]`, `-ERR [SYS/TEMP]`, or
SMTP `421 4.7.0` before the connection closes. These limits do not protect
accounts; failed-authentication throttling does that independently of them
and of exemptions (10 failures per account from one IP and 50 per IP per 15 minutes,
counting only failed attempts).

Behind a TCP load balancer (HAProxy, nginx `stream`, a cloud network load
balancer, or container port forwarding), every connection would otherwise
appear to come from the proxy. On the listeners named in `mail_proxy_protocol`,
a connection from a `mail_proxy_protocol_trusted` address must start with a
PROXY protocol header (v1 text or v2 binary, TCP over IPv4 or IPv6) within
5 seconds. The relayed client address then replaces the socket address
everywhere: per-IP connection admission and the flood guard,
failed-authentication throttling, greylisting, SPF, DNSBL and spam scoring,
HELO checks, DMARC reports, logs, metrics, and audit. A missing, malformed,
oversized (v1 over 107 bytes, v2 address block over 1024 bytes), or slow header
closes the connection; there is no fallback to the proxy's address. A `LOCAL`
(v2) or `UNKNOWN` (v1) header, as sent by proxy health checks, keeps the socket
address. Connections from other addresses are served directly with their own
address and closed if they send a PROXY header, so a client cannot spoof its
address. On implicit-TLS listeners the header precedes the TLS handshake. Both
settings apply live to running listeners.

### SMTP connection screening

The inbound SMTP listener (port 25) screens unauthenticated clients before and
during the session, Postfix postscreen style, without a separate daemon.
Loopback and the `mail_connection_limit_exempt` networks are never screened;
submission listeners are not screened. The client is the effective (PROXY
protocol) address.

| TOML key | Default | Meaning |
|---|---:|---|
| `smtp_greet_delay_ms` | `2000` | Milliseconds the greeting is held back after its first `220-` line; a client that sends anything before the final `220 ` line is an early talker. A client that waited is remembered for 24 hours and greeted at once (bounded cache by address). 0-6000; `0` disables the test |
| `smtp_pregreet_action` | `score` | `off` disables the greeting test; `score` adds `SMTP_PREGREET` to the client's messages, strikes the client with the ban engine, and serves the session; `reject` also answers `554 5.7.1` and disconnects |
| `smtp_protocol_violation_limit` | `10` | Protocol violations after which the session is answered `421 4.7.0` and closed with a ban strike; 0-1000, `0` never closes |
| `smtp_tarpit_after_unknown_rcpts` | `5` | Unknown recipients in one session after which every further RCPT reply is delayed one second more than the last, up to 10 seconds per reply, and `SMTP_RCPT_UNKNOWN` is scored; 0-1000, `0` disables |
| `smtp_fcrdns_check` | `true` | Check forward-confirmed reverse DNS of public clients and score `RDNS_NONE`, `RDNS_NOT_FCRDNS`, and `RDNS_DYNAMIC` |

Counted violations are: early talking; commands sent before a reply when
PIPELINING was not negotiated (before EHLO or after HELO) and EHLO, HELO,
DATA, STARTTLS, AUTH, NOOP, VRFY, or EXPN followed by more data in the same
read (`SMTP_PIPELINING`, also a ban strike); a bare-LF command line (once per
session), NUL bytes, command lines over 2048 octets (AUTH up to 12288; longer
lines are discarded and answered `500 5.5.2`), unknown commands, more than 100
RSET, NOOP, VRFY, or EXPN commands per accepted message, AUTH in cleartext on
port 25, and a bare LF around the end-of-data marker
(`SMTP_PROTOCOL_VIOLATION`). Command errors keep feeding
`ban_protocol_errors` and unknown recipients `ban_rcpt_unknown` as before.

Every fact the session observed flows into each transaction's spam evaluation
as a symbol, together with HELO checks for public clients: `HELO_BARE_IP` (an
unbracketed IP address), `HELO_NOT_FQDN` (no dot), and `HELO_FORGED_LOCAL`
(this server's `smtp_server_name` or exactly a hosted domain). The FCrDNS check
reuses the PTR name found by the HELO policy, looks up at most five names and
their addresses once per client address with a 3-second budget, caches the
outcome for an hour, and never scores a temporary DNS failure. A name counts as
dynamic when a label left of its registered domain contains a word such as
`dsl`, `dyn`, `pool`, `dialup`, `ppp`, `dhcp`, `cable`, `cpe`, or `customer`,
or when it embeds the IPv4 address (dotted, dashed, reversed, zero-padded, or
hex). All symbols accept `antispam_symbol_scores` overrides. All five settings
apply to the next session.

### Abuse auto-ban

The built-in ban engine (fail2ban-like) counts abuse strikes per client network
and bans a network that reaches a trigger's threshold within its window. A
banned client is refused before any protocol bytes: SMTP, IMAP, POP3, and
ManageSieve connections are closed at accept, and HTTP requests (web, DAV,
JMAP, EAS, EWS, MCP) receive a bare `403`. The client is always the effective
one: the PROXY protocol address on mail listeners and the address resolved
through `http_trusted_proxies` on HTTP.

| TOML key | Default | Meaning |
|---|---:|---|
| `ban_enabled` | `true` | Count strikes and enforce bans; while off, nothing is counted or refused and the ban table is kept |
| `ban_auth_failures` | `20/10m` | `count/window` of failed password logins (SMTP AUTH, IMAP, POP3, ManageSieve, web sign-in and step-up, DAV, JMAP, EAS, EWS) that bans the client network; throttled attempts count too |
| `ban_second_factor_failures` | `10/10m` | `count/window` of failed authenticator or recovery codes at web sign-in |
| `ban_rcpt_unknown` | `20/10m` | `count/window` of SMTP recipients (RCPT or VRFY) rejected as unknown in unauthenticated sessions (directory harvesting) |
| `ban_protocol_errors` | `30/10m` | `count/window` of SMTP `500`-`504` command errors in unauthenticated sessions |
| `ban_spamtrap_hits` | `1/24h` | `count/window` of unauthenticated messages to `antispam_spamtraps` addresses; one hit bans by default because no legitimate sender knows a trap |
| `ban_durations` | `[10m 1h 1d 1w]` | Ban lengths for a network's first, second, third, and later offenses; the last repeats. Go durations plus whole days (`d`) and weeks (`w`), 1 minute to 3650 days, never decreasing |
| `ban_ipv6_prefix` | `64` | IPv6 clients are grouped and banned by this prefix (32-128); IPv4 clients are banned as single addresses |

Windows accept 10 seconds to 24 hours; a count of `0` (or the value `0`)
disables a trigger. A ban expires on its own; an expired ban still escalates
the next ban of the same network for 30 days. Loopback, the
`mail_connection_limit_exempt` networks, and the `http_trusted_proxies`
networks are never struck, banned, or refused, so put shared office or carrier
NAT addresses and gateways there. A successful login clears its network's
strikes and shields it from new strikes for the trigger window. Bans persist
in the system store (namespace `bans`) across restarts. All ban settings, and
the shared exemptions, apply live.

Administrators manage bans under Admin → Bans: active bans with reason,
strikes, offense, expiry, and refused-connection hits, search, manual ban of an
address or CIDR prefix (refused for loopback, exempt networks, and the
administrator's own address), and unban, which also forgets the network's
escalation history. The API is `GET /api/v1/admin/security/bans?q=`, `POST
/api/v1/admin/security/bans` with `{"network","duration","comment"}` (an empty
duration follows the escalation schedule), and `DELETE
/api/v1/admin/security/bans?network=`. Bans and unbans are audited as
`security.ban.add` (actor `system` for automatic bans) and
`security.ban.remove`. Metrics are `ban_active`, `ban_created_total{reason}`,
and `ban_refused_total{surface}`. Runtime health shows an `abuse-bans`
component that warns only when 10,000 or more bans are active; the table holds
at most 100,000.

SMTP, IMAP, POP3, and ManageSieve settings apply live, without a restart:
enable flags, listen addresses, server names, certificate assignments,
TLS-for-authentication requirements, `imap_max_literal_size`, SMTP session
limits, connection screening, and SPF/DKIM/DMARC/spoofing policies, `smtp_auth_mechanisms`,
`ntlm_enabled`, `sasl_ir_enabled`, the mail connection limits, and the PROXY protocol settings. A listener whose address is unchanged
keeps accepting and gives its next sessions the new settings. A moved or newly
enabled listener is bound before the old one stops. Connected clients are
never dropped: a stopped listener's sessions run to completion and are drained
at shutdown. A certificate assignment applies to the next TLS handshake without
rebinding. Veksel loads the certificate and binds every new address before
changing anything, so a certificate that cannot load or an address already in
use marks the change `failed` and leaves the running listeners alone. A
listener that needs a certificate when none is assigned is skipped and reported
in the protocol status, as at startup. A protocol stopped from the
administration UI stays stopped across configuration changes. Those changes are
still validated, and the next start uses them. Changing `smtp_public_address`
re-runs the mail identity check.

### Recipient addressing and forwarding

The three `user_aliases_*` keys apply live. See
[Temporary aliases](#temporary-aliases) below the resolver description.

| TOML key | Default | Meaning |
|---|---:|---|
| `recipient_delimiter` | `+` | Subaddress delimiters; each character separates a user from a detail. Empty disables subaddressing |
| `user_aliases_enabled` | `true` | Let users create temporary (disposable) aliases; existing aliases keep working when turned off |
| `user_aliases_max_per_user` | `50` | Most unexpired temporary aliases one account may hold (1-10000) |
| `user_aliases_domains` | empty (all hosted domains) | Hosted domains where users may create temporary aliases |
| `srs_enabled` | `true` | Rewrite the envelope sender of forwarded and redirected mail with the Sender Rewriting Scheme |
| `srs_domain` | empty (SMTP server name) | Domain of rewritten senders |

Every local recipient lookup (SMTP RCPT and delivery, generated mail, queue
routing, and quarantine ownership) uses one resolver. The most specific match
wins: an exact email identity, an exact recipient alias, then the subaddress
base, so `user+detail@domain` delivers to `user@domain` (or that alias) when
no exact address exists. As in Postfix, the local part is split at the first
delimiter character and the user part must not be empty. The detail stays in
the envelope recipient, where Sieve's `envelope` test and `subaddress`
extension (`:user`, `:detail`) see it. A disabled identity or alias is a match
and is rejected rather than falling through to a broader one.

Each domain may name a catch-all address in domain administration. It must be
an enabled local identity, which cannot then be deleted while it is the
catch-all. The catch-all receives mail only when no exact, alias, or
subaddress match exists. It never receives SRS addresses, and a domain that is
not hosted is still rejected.

#### Temporary aliases

With `user_aliases_enabled`, a user creates disposable addresses in User
settings, Temporary aliases (or `POST /api/v1/user/aliases`) on the hosted
domains of their own identities, restricted to `user_aliases_domains` when
that list is not empty. The address is eight random characters, optionally
after a prefix (`shop-x7k2m9q3@example.com`), unique among identities,
recipient aliases, temporary aliases, and tombstones. An alias may expire
after one day, one week, one month, or never; it carries an optional label and
an optional delivery folder (blank is the Inbox). It sits in the resolver
after the exact recipient alias, so a subaddress such as `alias+tag@domain`
also reaches it, and quarantine ownership and Sieve see the owner.

An expired or disabled alias never falls through to the catch-all. Per alias,
mail is either rejected at RCPT as an unknown recipient (550) or accepted and
silently discarded. While active, an alias is also a sending identity of its
owner (listed in the compose identities), so replies need not reveal the real
address; nobody else can send as it and delegation does not apply.

Aliases count toward the domain's `max_aliases` limit and
`user_aliases_max_per_user` while unexpired. Administrators see an account's
temporary aliases in the account details and can disable one so the owner
cannot re-enable it (`PUT /api/v1/admin/users/{id}/aliases/{address}/lock`).
Turning `user_aliases_enabled` off stops new aliases only.

An hourly job turns aliases that expired more than seven days ago into
tombstones; deleting an alias does the same at once. A tombstone keeps no
settings, rejects mail, and reserves the address for 90 days before it is
released, so the address cannot be reissued to another account. Mail that a
local user sends through the queue to an alias lands in the owner's Inbox
rather than the alias's delivery folder, and a discarding alias then bounces
for that sender.

Account forwarding and Sieve `redirect` from a remote sender use an SRS0
envelope sender at `srs_domain`, so the forwarded copy passes SPF at the
destination. The domain's SPF must authorize this server and its MX (or
address record) must reach it. Null senders, senders in hosted domains, and
senders already at `srs_domain` keep their address; an SRS sender from another
forwarder becomes SRS1. Addresses use the libsrs2 format: a four-character
HMAC-SHA1 hash, compared case-insensitively, and a day-granular timestamp.
Inbound mail to an SRS address at `srs_domain` is verified and relayed through
the outbound queue to the original sender. A forged address, or one older than
21 days, is refused with `550 5.1.1`. Returns are still verified while
`srs_enabled` is off, so mail forwarded earlier can bounce. The signing secret
is generated on first start and kept in the system store. The stored list
signs with its first secret and verifies with all of them, so a new secret can
be prepended while older addresses circulate. All three settings apply live.

### Signed return paths (BATV)

| TOML key | Default | Meaning |
|---|---:|---|
| `batv_enabled` | `false` | Sign the envelope sender of mail from hosted domains and reject untagged bounces to local addresses |
| `batv_grace_period_hours` | `168` | Hours after enabling during which untagged bounces are still accepted |

Bounce Address Tag Validation (draft-levine-smtp-batv) protects local
addresses from backscatter: bounces and auto-replies to mail that spammers
sent with a forged local sender. With `batv_enabled`, every remote delivery
whose envelope sender is in a hosted domain is sent with the standard prvs
form `prvs=KDDDSSSSSS=user@domain`, where `K` is a key digit, `DDD` the day
number, and `SSSSSS` a truncated HMAC-SHA1 over both and the address. The
queued message, message trace, and the RFC 5322 headers keep the original
address; the null sender, SRS senders, and senders at other domains are never
signed.

Unauthenticated mail with a null envelope sender (`MAIL FROM:<>`) to a hosted
domain must then name a valid tagged recipient no older than seven days;
otherwise the recipient is refused with `550 5.7.1` as backscatter. A valid
tag is removed before alias, subaddress, catch-all, and mailbox lookup, so the
bounce reaches `user@domain`. `postmaster` and `abuse`, and SRS addresses
(which SRS verifies), never require a tag. For `batv_grace_period_hours` after
enabling, untagged bounces are still accepted so bounces to mail sent before
signing began arrive; the enable time is stored and survives restarts, and
disabling clears it. Tags keep verifying while BATV is off, so mail sent
earlier can still bounce.

BATV is off by default because some receivers mishandle tagged senders:
mailing lists that match subscribers by envelope sender reject or re-subscribe
the changing address, and some greylisting and allow-list implementations see
a new sender for each day. Enable it when backscatter is a problem and the
domains' correspondents tolerate it. The signing secret is generated on first
start and kept in the system store next to the SRS secrets with the same
rotation model: the first listed secret signs and every listed secret
verifies. Both settings apply live.

### Mail flow rules

Sender-dependent routes, address rewriting, journaling, and always-BCC are
administrative objects rather than TOML settings. They are edited in
Administration › Mail flow or through `/api/v1/admin/mail-flow` (`GET` lists
every kind; `POST /api/v1/admin/mail-flow/{kind}`, `PUT` and `DELETE
/api/v1/admin/mail-flow/{kind}/{id}`, where `kind` is `sender-routes`,
`rewrites`, `journal`, or `bcc`). Every change is audited as
`mail_flow.<kind>.create|update|delete`, and delivery reads the rules for
each message, so a change applies to the next message without a restart.
Address patterns are an exact address (`user@example.com`) or a domain
(`example.com` or `@example.com`); an exact pattern wins over its domain.

**Sender-dependent routes** pick the next hop for remote recipients by the
envelope sender (`sender`), the authenticated account (`account`, an account
ID or `@domain`), or both, optionally only for one `destination` domain.
Route precedence is: a matching sender route with a destination, a matching
sender route without one, the per-domain outbound route, the global smart
host (`relay_host`), then direct MX. Mail-policy and administrative
reroutes still come first. A route is `relay` (host and port) or `mx`, with
`require_tls` (refuse a next hop without STARTTLS; otherwise opportunistic)
and `tls_skip_verify`. Relay credentials are sealed with the installation's
stored-credential keys (the same keys as synchronization credentials, bound
to the route ID), opened only for the delivery that uses them, and never
returned by the API: responses show `has_password`, an update without
`password` keeps the stored one, and an empty `password` removes it. An
enabled sender route also makes its destinations relayable for
authenticated submission.

**Address rewriting** (canonical maps) replaces an address. `outbound`
rules rewrite the envelope sender and/or the From header of locally
originated mail (authenticated submissions and server-generated mail) once,
at queue admission, before mail policy and DKIM signing, so the signature is
made for the rewritten domain; a domain replacement keeps the local part, so
`@internal.example → @example.com` turns `joe@internal.example` into
`joe@example.com`. The applied rewrite is recorded on the queued message
(`address_rewrite`). `inbound` rules rewrite envelope recipients at SMTP
`RCPT` (before alias expansion and backscatter checks) and wherever a
recipient is resolved (masquerading). Rewriting is a single pass and rules
cannot chain: a rule whose replacement another rule of its direction would
match, or whose pattern matches another rule's output, is refused, so
rewriting can never loop. Rewriting differs from aliases: an alias keeps
the envelope recipient and adds delivery targets, while a rewrite changes
the address itself, before aliases are expanded.

**Journaling** copies every message matching a rule to a journal address.
A rule names a hosted `domain` (empty for all), `inbound` (mail with a
recipient at the domain) and/or `outbound` (mail a local account submitted
from the domain), the journal `address` (a local mailbox or an external
address), and a `format`: `envelope` (the default) sends an
Exchange-style report whose text part lists the sender, subject,
Message-ID, direction, and every envelope recipient typed `To`, `Cc`, or
`Bcc` (recipients absent from the headers, including always-BCC copies),
followed by the original as `message/rfc822`; `raw` sends the original
with `X-Veksel-Journal`, `X-Veksel-Journal-Direction`,
`X-Veksel-Journal-Sender`, and one `X-Veksel-Journal-Recipient` per envelope
recipient. Copies are made once per SMTP transaction or submission, join the
same atomic queue batch as the original (so the original is never accepted
without them), carry the null sender and `NOTIFY=NEVER`, and link to the
original in message trace as derived `journal` messages. They skip spam
scoring, rewriting, sending limits, BATV signing, and mailbox quotas, and
are never journaled again; mail addressed only to journal addresses is not
journaled, which stops loops through an external journal.

**Always BCC** adds a blind copy recipient by envelope sender or by each
envelope recipient, with Postfix `sender_bcc_maps` and `recipient_bcc_maps`
semantics: an exact-address rule hides the rules for its domain, a copy is
not added for an address that already receives the message, and copies keep
the original sender and any send-guard hold but never return delivery
status notifications.

### Calendar email invitations

| TOML key | Default | Meaning |

### OpenPGP key discovery

| TOML key | Default | Meaning |
|---|---:|---|
| `wkd_enabled` | `true` | Serve user-published OpenPGP public keys over the Web Key Directory for hosted domains |
| `autocrypt_enabled` | `false` | Add an `Autocrypt` header to outgoing mail from identities that turned it on |

Users publish the public key of each of their enabled identities under User
settings › Encryption keys: an ASCII-armored or binary key, validated on
upload. Veksel refuses private keys, garbage, revoked or expired keys, keys
without an encryption subkey, and keys without a user ID for exactly that
address. It stores a minimal key (primary key, the matching user ID with its
self-signature, and the newest valid encryption subkey; other user IDs and
third-party certifications are dropped) and shows its fingerprint and expiry.

With `wkd_enabled`, Veksel answers the Web Key Directory
(draft-koch-openpgp-webkey-service) for hosted domains only, and only for
enabled identities with a published, unexpired key: the advanced method
`https://openpgpkey.<domain>/.well-known/openpgpkey/<domain>/hu/<hash>?l=<local>`
and the direct method `https://<domain>/.well-known/openpgpkey/hu/<hash>?l=<local>`,
each with an empty `policy` file. `<hash>` is the z-base-32 SHA-1 of the
lower-cased local part. Keys are sent as `application/octet-stream` with
`Access-Control-Allow-Origin: *`. The paths sit under `/.well-known/`, so an
HTTPS listener must carry the autodiscover service and the host names must
reach it. The expected DNS records then include `openpgpkey.<domain>` as a
CNAME to the SMTP server name (see
[Deployment](deployment.md#7-dns-for-mail)).

With `autocrypt_enabled`, outgoing mail submitted by an account carries
`Autocrypt: addr=…; prefer-encrypt=nopreference; keydata=…` when the sender
address has a published key and its Autocrypt toggle is on. The header is
added at queue admission, after address rewriting and before the DKIM
signature, and only when the account owns the key. A key over 10 KB is not
advertised (a warning is logged and the Encryption keys page says so). Both
settings apply live.

A local account marked as a room or equipment resource (Administration › Rooms
& equipment) answers invitations itself: it accepts a request when it is free,
declines one that overlaps an existing booking unless overlaps are allowed, or,
with the approval policy, leaves it for a delegate of its calendar to answer.

### Reverse proxies

| TOML key | Default | Meaning |
|---|---:|---|
| `http_trusted_proxies` | `[]` | IP addresses or CIDR prefixes (for example `['127.0.0.1', '10.0.0.0/8']`) of reverse proxies in front of the HTTP(S) listeners |
| `http_forwarded_header` | `x-forwarded` | The one forwarding header family the trusted proxies set: `x-forwarded` (`X-Forwarded-For`/`-Proto`/`-Host`, `X-Real-IP`) or `forwarded` (RFC 7239) |

Veksel ignores the RFC 7239 `Forwarded` header and `X-Forwarded-For`,
`X-Real-IP`, `X-Forwarded-Proto` and `X-Forwarded-Host` unless the connecting
peer is inside one of these prefixes; the default trusts nobody. Only the
family named by `http_forwarded_header` is read; the other is ignored even
from a trusted peer, because proxies such as HAProxy, nginx and Traefik add
`X-Forwarded-For` but pass a client's own `Forwarded` header through
unchanged. With `forwarded`, a request without a usable `Forwarded` header
resolves to the proxy's own address.

For a trusted peer, the forwarded hops (`for=` in `Forwarded`, or the
`X-Forwarded-For` list) are walked right to left, skipping trusted hops, and
the first untrusted address becomes the client IP used by login throttling,
sessions, audit records and access logs, so a client cannot spoof its address
by prepending entries. `X-Real-IP` is used only when `X-Forwarded-For` is
absent. `Forwarded` elements may span several header lines; quoted values,
bracketed IPv6 addresses (`for="[2001:db8::1]:443"`) and ports are accepted.
An `unknown` or obfuscated (`_hidden`) node, or a malformed element, stops the
walk at the last good address. Headers over 8 KiB are ignored and at most 32
hops are examined.

The effective scheme and host decide whether session cookies are `Secure`, HSTS
on proxied HTTP listeners, and which origin JMAP session URLs advertise. With
`Forwarded`, they come from the `proto=` and `host=` of the walked element
nearest the client. With `X-Forwarded-*`, the rightmost `X-Forwarded-Proto` and
`X-Forwarded-Host` values (those supplied by the nearest proxy) are used;
configure the proxy to overwrite, not append, these two headers. Invalid
entries are rejected when the configuration is saved, and changes apply
without a restart.

HSTS (`hsts_max_age_days`, `hsts_include_subdomains`, `hsts_preload` on an
`[[http_listeners]]` entry) is sent on every response of an HTTPS listener. It
may also be configured on an HTTP listener behind a TLS-terminating proxy: it
is then sent only when a trusted proxy reports that the client connected over
HTTPS, and never on a genuinely plain-HTTP request or for an untrusted peer.

### Two-factor web sign-in

| TOML key | Default | Meaning |
|---|---:|---|
| `web_two_factor_required` | `off` | Accounts that must use a second factor at web sign-in: `off`, `administrators` (accounts with system administration rights), or `all` |
| `two_factor_requires_app_passwords` | `true` | Accounts with a second factor must use application passwords on IMAP, SMTP submission, POP3, DAV, JMAP, ManageSieve, EWS and ActiveSync, which cannot ask for the factor; their primary password then signs in to the web only. A refused primary password does not count toward throttling or bans. Applies live |

Users enrol under **Settings → Two-factor sign-in**: an authenticator app
(RFC 6238 TOTP: SHA-1, six digits, 30-second steps, one step of clock skew)
confirmed with a code from the app, and any number of WebAuthn security keys or
passkeys (up to 20). The first factor issues ten single-use recovery codes,
shown once and stored only as salted hashes; they can be regenerated, which
invalidates the previous set. TOTP seeds are sealed with the same AES-256-GCM
envelope keys as synchronization credentials, bound to the account; key
rotation keeps old keys readable, so it does not strand enrolled seeds. A code
is refused once its time step, or an earlier one, has been accepted.

After a correct password, an account with factors receives a pending sign-in
(its own five-minute cookie) that grants nothing except the second-factor step;
the code, recovery code, or security key replaces it with a new session.
Second-factor attempts share the failed-login throttle (with a separate
per-account budget that a correct password does not reset), and five failures
end the pending sign-in. The JSON sign-in API (`POST /api/v1/session/login`)
reports `second_factor` and is completed with
`POST /api/v1/session/second-factor`.

The policy applies live to the next sign-in; existing sessions are not ended.
An account it covers that has no factor is taken through enrolment, as part of
sign-in, before it receives a session, and cannot remove its last factor.
Administrators reset a user's factors from the account editor
(`DELETE /api/v1/admin/users/{id}/two-factor`); with the server stopped,
`veksel reset-password --clear-2fa` does the same (see the deployment guide).
Removing a factor, regenerating recovery codes, and enrolling another factor
on an account that already has one require the account password again (a
`password` field in the request body); it is checked under the same per-account
failed-login throttle, and a wrong password is refused with 403 and audited as a
failure. Enrolling a first factor and renaming a key need no password.
Enrolment, removal, reset, recovery-code use, sign-in and failures are audited
as `account.two_factor.*`.

WebAuthn binds a credential to the host name the browser addressed: the
relying-party ID and origin follow the request host and scheme, honouring
`http_trusted_proxies` like session cookies. A key registered on one host name
does not work on another, and browsers offer WebAuthn only over HTTPS or on
`localhost`.

Second factors protect browser sign-in only. Protocol logins (IMAP, SMTP,
POP3, DAV, JMAP, EWS, EAS, ManageSieve) keep using application passwords, REST
and MCP API keys are unaffected, and an administrator starting impersonation or
delegation does not need the subject's factors.

| TOML key | Default | Meaning |

| `ldap_urls` | `[]` | Directory servers (`ldaps://host[:port]` or `ldap://host[:port]`), tried in order for failover |
| `ldap_allow_plaintext` | `false` | Use `ldap://` without StartTLS, sending passwords in clear text; isolated test networks only |
| `ldap_ca_certificate` | empty | PEM certificate authorities trusted for the directory instead of the system roots |
| `ldap_bind_dn` | empty | Service account used to search for users; empty searches anonymously |
| `ldap_bind_password` | empty | Service account password; sensitive, never returned or logged |
| `ldap_base_dn` | empty | Subtree searched for users; required when enabled |
| `ldap_user_filter` | see below | Filter that must match exactly one entry for a login; `{login}` is replaced by the escaped login |
| `ldap_id_attributes` | `[sAMAccountName uid]` | The first present attribute, lowercased, becomes the local account ID |
| `ldap_admin_group_dn` | empty | Direct members get administration with the role chosen by `ldap_admin_role`; only a system owner can change it |
| `ldap_admin_role` | `owner` | Role the administrator group grants: `owner` (`system.owner`, unrestricted) or `admin` (`system.admin`, operational administration without owner authority); only a system owner can change it |
| `ldap_sync_filter` | `(&(objectClass=person)(!(objectClass=computer)))` | Every user the sync considers; directory accounts it does not match are disabled |
| `ldap_sync_interval_minutes` | `60` | Minutes between scheduled syncs; `0` turns scheduled sync off |
| `ldap_timeout_seconds` | `10` | Seconds allowed for each connection attempt and directory request |

The default sign-in filter is
`(&(objectClass=person)(|(uid={login})(mail={login})(sAMAccountName={login})(userPrincipalName={login})))`,
so users can sign in with their user name, UPN, or email address. Every
setting applies live and is managed under **Administration → Directory (LDAP)**,
which also shows the last sync result and account counts and offers
**Test connection** (`POST /api/v1/admin/directory/test`: connect, service
bind, a sample search and the administrator group, returning a diagnostic
that never contains the password) and **Sync now**
(`POST /api/v1/admin/directory/sync`). `GET /api/v1/admin/directory` returns
the status.

**Sign-in.** Browser sign-in and every protocol login (IMAP, SMTP, POP3,
ManageSieve, DAV, JMAP, EWS, EAS, Autodiscover) use one password check. An
account with a local password is checked only against its local hash and never
consults the directory, so the owner and other local accounts keep working when
the directory is down or misconfigured. A directory account is checked only
against the directory: Veksel searches with the service account, requires
exactly one entry, and binds as that entry with the supplied password. An empty
password is refused before any request, so an unauthenticated bind can never
succeed. A login matching no local account goes to the directory too, and a
successful bind provisions the account. Application passwords are local
credentials and keep working for directory accounts, also while the directory
is unreachable; they are tried before the directory so a mail client's app
password never counts toward the directory's lockout. The failed-login throttle
applies to every attempt, and enrolled second factors are still required at web
sign-in after the directory password succeeds.

**Transport.** `ldaps://` uses TLS; `ldap://` requires StartTLS unless
`ldap_allow_plaintext` is on. Certificates are verified against the system
roots, or only against `ldap_ca_certificate` when it is set, and must name the
host in the URL. Service-bound connections are pooled and rebound as the
service account after each user bind; servers are tried in order, starting with
the last one that answered.

**Provisioning.** On first sign-in the account ID is the first present
`ldap_id_attributes` value, lowercased; it must be a valid account ID (no `@`,
`:`, `/`, `\` or whitespace). If a local, non-directory account already has that
ID, or a directory account with a different `objectGUID`/`entryUUID` does, the
sign-in is refused and logged (`directory.account.conflict`) rather than taking
the account over. The display name comes from `displayName`, then `cn`. Email
identities are added from `mail` and `proxyAddresses` (`SMTP:` primary first,
then `smtp:`) only on hosted, enabled domains, and never when another account
owns the address; the first becomes primary. The account records its DN and
`objectGUID` or `entryUUID`, so a renamed entry still finds its account.
Directory identities are only added: addresses removed in the directory stay
until an administrator removes them.

**Administrators.** When `ldap_admin_group_dn` is set, direct members (the
group's `member`, `uniqueMember` or `memberUid`, or the user's `memberOf`) get
an administrator role, which opens administration: the system owner role by
default (`ldap_admin_role = 'owner'`, the original behavior), or the system
administrator role with `ldap_admin_role = 'admin'`. A system administrator
has full operational administration but cannot assign roles or ownership,
restore backups, change raw configuration or these two settings, or reach a
system owner's account (see [Authorization](authorization.md#administrative-roles)).
Changing the setting replaces the directory's binding at each member's next
sign-in or sync. Membership is re-evaluated at every sign-in and sync; leaving
the group revokes only the binding the directory granted, never one given by
an administrator. Nested groups are not expanded. Because the group confers
administration, protect it in the directory accordingly.

**Sync.** Scheduled and manual syncs list the users matching
`ldap_sync_filter` (at most 100,000; a larger result fails the sync rather than
act on a partial list), refresh each directory account's display name, DN,
addresses and administrator role, and disable accounts whose entry is gone or
has Active Directory's `ACCOUNTDISABLE` flag (`userAccountControl` bit 2).
Disabling ends their sessions but keeps all data; nothing is deleted. An
account sync disabled is re-enabled when its entry returns, while an
administrator's own disable is kept. A failed search, or one returning no
entries at all, disables nothing. Syncs never create accounts; first sign-in
does. The last result is persisted, so the schedule resumes after a restart,
and syncs, provisioning, role changes and disables are audited as
`directory.*`.

**Passwords.** A directory account's password cannot be changed or reset in
Veksel: the user settings page explains where to change it, and the profile and
administrator APIs answer 409. `reset-password` refuses directory accounts too;
keep at least one local owner as the break-glass account.

### Built-in DNS server

Zones whose DNS provider is `builtin` are served by Veksel' own authoritative
DNS server, for operators without a DNS hosting API. Publishing, DKIM rotation,
and ACME DNS-01 work against it exactly as against an external provider.

| TOML key | Default | Meaning |
|---|---:|---|
| `dns_server_enabled` | `false` | Answer DNS queries for `builtin` zones over UDP and TCP |
| `dns_server_listen` | `0.0.0.0:53` | UDP and TCP bind address; port 53 needs `CAP_NET_BIND_SERVICE` or root |
| `dns_server_nameservers` | `[]` | NS names published at every zone apex, the first being the SOA primary (at most 13). Empty publishes the SMTP server name |
| `dns_server_dnssec` | `false` | Sign answers online with each zone's ECDSA P-256 key (algorithm 13) |
| `dns_server_axfr_tsig` | empty | Zone transfer key as `[algorithm:]name:base64-secret` (dig `-y` form, default `hmac-sha256`, at least 16 secret bytes); empty refuses transfers. Redacted like passwords |

All five settings apply live: a new address is bound for both transports
before the old sockets close (a failed bind keeps the running server), and
nameserver, DNSSEC, and transfer changes take effect on the next query. The
listener must not collide with another enabled TCP listener. Health reports a
`dns-server` component while the server is enabled.

The server is authoritative only. It answers with the AA flag for names in a
hosted zone, synthesizes the apex SOA (serial `YYYYMMDDnn`, bumped on every
record change; refresh 3600, retry 900, expire 1209600, negative TTL 300) and
NS records, follows CNAME chains inside the zone, and adds in-zone glue to NS
answers. Missing names get NXDOMAIN and missing types NODATA, both with the
SOA in the authority section. Everything else is refused:

- Names outside the hosted zones, non-IN classes, and recursion requests get
  REFUSED; non-query opcodes get NOTIMP and EDNS versions above 0 BADVERS.
- UDP responses are rate limited per client network (IPv4 /24, IPv6 /56) at
  20 responses per second with a two-second burst; over the limit every
  second response is a truncated empty reply that moves real clients to TCP
  and the rest are dropped. TCP is not rate limited.
- UDP responses are capped at 512 bytes without EDNS and at the client's
  EDNS buffer size, at most 1232 bytes, and truncated (TC) beyond that so
  clients retry over TCP.
- ANY queries get a single synthesized `HINFO "RFC8482"` record (RFC 8482).
- AXFR and IXFR (always answered as a full transfer) are accepted only over
  TCP with a valid TSIG signature from the `dns_server_axfr_tsig` key; they
  are refused while DNSSEC signing is on because online signing leaves no
  NSEC chain to transfer. Secondaries poll the SOA; Veksel sends no NOTIFY.

With `dns_server_dnssec`, each zone's combined signing key (flags 257) is
published as a DNSKEY and every answer to a client that sets the DO bit
carries online RRSIGs (valid seven days, refreshed after half of that).
Nonexistence is proven with compact denial (RFC 9824): a NOERROR reply with
one signed NSEC record at the queried name whose next name is its immediate
successor, listing the existing types, or the NXNAME type for a name that
does not exist. Clients without DO keep receiving unsigned answers and real
NXDOMAIN. Private keys are sealed with the stored-credential keys and never
leave the server; the zone records view shows the DS record to give the
registrar. Rollover is manual and two-step: stage a new key (published but
not signing), add its DS record at the registrar and wait for the old DS
record's TTL, then activate it, which makes it sign and removes the old key.

### Outbound MTA-STS

RFC 8461 MTA-STS policy application is automatic for direct MX delivery,
global smart-host delivery, and per-domain outbound routes. Smart hosts use
the configured relay hostname as the policy domain; direct delivery uses the
exact recipient domain and never walks to a parent domain. Address literals
do not participate.

Policy discovery uses `_mta-sts.<domain>` and the fixed HTTPS policy URL. The
system-store cache records the policy ID, fetch and expiry times, last check,
and bounded failure state. A valid unexpired cache remains authoritative when
DNS or HTTPS is unavailable. Enforce-mode validation cannot be weakened by a
route's skip-verification option, and failures defer queued delivery with
enhanced status `4.7.5`. There are no environment-variable controls for this
behavior. Cache visibility and explicit refresh are available in the managed
Outbound TLS administration workspace.

### Outbound DANE

RFC 7672 DANE authenticates direct MX delivery with DNSSEC-signed TLSA
records. It does not apply to the global smart host or per-domain routes
(operator-chosen next hops), or to messages sent with `TLS-Required: No`.

| Setting | Default | Meaning |
|---|---|---|
| `dane_enabled` | `true` | Look up `_25._tcp.<mx-host>` TLSA records and enforce them for direct MX delivery |
| `dane_resolvers` | `[]` | Trusted DNSSEC-validating resolvers (`IP` or `IP:port`, port 53 by default); empty uses only the loopback resolvers in `/etc/resolv.conf` |

Go's resolver does not validate DNSSEC, so Veksel queries with the DNSSEC OK
bit and trusts the resolver's Authenticated Data (AD) bit. That bit is only
meaningful from a validating resolver over a trusted path, so with an empty
`dane_resolvers` Veksel trusts only loopback system resolvers (for example
unbound or systemd-resolved with `DNSSEC=yes`) and ignores remote ones. Listing
addresses in `dane_resolvers` asserts that they validate and that the path to
them cannot be tampered with. Without a trusted resolver DANE stays inactive
and delivery uses MTA-STS and opportunistic TLS as before. Veksel probes the
resolver a minute after startup, every six hours, after a settings change, and
when the Outbound TLS page is opened: it must authenticate `isc.org` and refuse
the deliberately broken `dnssec-failed.org`. A resolver that fails the probe
deactivates DANE; the Outbound TLS page shows the state, resolvers and verdict.

Policy, per RFC 7672:

- An unsigned (insecure) MX RRset or unsigned MX address records mean no DANE
  for that domain or host. A secure MX RRset becomes the delivery target list.
- When a host has usable TLSA records, STARTTLS is mandatory and the
  certificate must match: DANE-EE(3) matches the leaf certificate or its public
  key and ignores names and dates; DANE-TA(2) requires a chain to the named
  trust anchor and a certificate name matching the MX host or the TLSA base
  domain. PKIX-TA(0) and PKIX-EE(1) records are unusable for SMTP; a host with
  only unusable records still requires STARTTLS without authentication.
- DANE takes precedence over MTA-STS for a host with TLSA records.
- SERVFAIL (a DNSSEC validation failure on a signed zone) or a resolver error,
  a missing STARTTLS, or a certificate mismatch defers delivery through that
  host with enhanced status `4.7.5`; it never bounces. A REQUIRETLS message may
  use a host with usable TLSA records instead of an enforcing MTA-STS policy.

Each queue attempt records its outcome (`dane-verified`, `no-dane`,
`dane-unauthenticated` or `dane-failed` with the reason) as `tls_policy` in the
attempt history and message trace. SMTP TLS reports use policy type `tlsa`
with the TLSA records as policy strings and the result types `tlsa-invalid`,
`dnssec-invalid`, `certificate-host-mismatch`, `certificate-not-trusted` and
`starttls-not-supported`.

### SMTP TLS reporting

RFC 8460 outcome recording is automatic for outbound SMTP. Veksel stores only
bounded daily policy/session aggregates in the generic system store; it does
not retain message content, envelope addresses, credentials, message IDs or
raw remote errors in reporting records. Duplicate queue attempts and
overlapping failure observations are durably deduplicated.

After a UTC reporting day closes, Veksel discovers `_smtp._tls.<domain>` and
delivers a deterministic gzip report to the published `rua` endpoints. HTTPS
delivery rejects redirects and unsafe address resolution. `mailto` delivery
uses an enabled hosted submitter domain with a configured DKIM key, builds a
standards-shaped multipart report, and enters the normal durable system queue.
Prepared payloads and retry state survive server restart. Delivery is retried
within the reporting window and never recursively contributes TLS failures to
another report. Effective policies and metadata-only report jobs are visible
in the pageable Outbound TLS administration workspace; there are no
environment-variable controls.

### ARC (authenticated received chain)

| TOML key | Default | Meaning |
|---|---:|---|
| `arc_verify` | `true` | Validate the ARC chain (RFC 8617) of inbound mail and report `arc=pass`, `arc=fail`, or `arc=none` in Authentication-Results |
| `arc_trusted_sealers` | `[]` | Forwarding domains (and their subdomains), such as `google.com` or `microsoft.com`, whose valid ARC seal can override a DMARC failure (up to 100) |
| `arc_seal_forwards` | `true` | Add an ARC set to account forwards and Sieve redirects, signed with the forwarding domain's active DKIM key |

The keys apply live with the other SMTP session settings.

**Verification.** Veksel validates the chain on the exact bytes the peer sent,
before adding its own header fields: every instance from 1 to the highest
present must appear exactly once with an ARC-Authentication-Results,
ARC-Message-Signature, and ARC-Seal; instances run from 1 to 50 without gaps;
the newest ARC-Message-Signature must verify against the message as received
(older ones may legitimately fail after a mailing list changed the message);
and every ARC-Seal must verify over the sets below it, with `cv=none` at
instance 1 and `cv=pass` above. A newest seal reporting `cv=fail` fails the
chain. Signatures use the DKIM key records, canonicalization, and RSA-SHA256
or Ed25519-SHA256 algorithms; RSA keys under 1024 bits are refused, and one
validation looks up at most eight distinct sealer keys. The
result is recorded as `arc=<result>` with the newest sealer as `header.d`
and, on failure, the reason.

**Trusted sealers and DMARC.** A forward or mailing list breaks SPF and often
DKIM, so DMARC fails for mail the original sender authenticated correctly. When
DMARC fails, the chain passes, the newest sealer is in `arc_trusted_sealers`,
and that sealer's ARC-Authentication-Results recorded `dmarc=pass`, Veksel
overrides the failure as RFC 7489 local policy: the message is neither
rejected nor quarantined, Authentication-Results keeps `dmarc=fail` with
`reason="arc trusted sealer <domain>"` and `policy.dmarc=none`, the aggregate
report records the disposition `none`, and spam scoring does not add
`DMARC_FAIL`. Only the newest seal counts, because only its message signature
must match the message as received; older sets can be copied from other
mail.

**Sealing.** A forward or redirect leaves with a new ARC set prepended: an
ARC-Authentication-Results carrying this hop's Authentication-Results, an
ARC-Message-Signature over the forwarded message (relaxed canonicalization;
From, To, Subject, Date, Message-ID, MIME, reply, and DKIM-Signature fields
that are present), and an ARC-Seal over the whole chain, all signed with the
active DKIM key of the recipient's hosted domain. Without an active key the
message is forwarded unsealed. A chain that failed, or was not verified
because `arc_verify` is off, is never extended, and neither is one already at
50 sets. The fields carry no timestamp, so sealing is deterministic and a
replayed forward keeps its queue identity.

### Inbound SMTP greylisting

Greylisting is disabled by default and applies only to unauthenticated inbound
SMTP, never authenticated submission. Recipient validity is checked first.
Triplets use a normalized source network, envelope sender, and recipient, but
only a SHA-256 identity is persisted; raw sender and recipient values are not
stored in the greylist triplet table.

| TOML key | Default | Meaning |
|---|---:|---|
| `greylist_enabled` | `false` | Temporarily defer unfamiliar inbound sender triplets |
| `greylist_minimum_delay_seconds` | `300` | Earliest acceptable retry after first observation |
| `greylist_retry_window_minutes` | `240` | Window in which a retry establishes a pass |
| `greylist_pending_lifetime_hours` | `24` | Retention for pending triplets |
| `greylist_pass_lifetime_days` | `36` | Sliding retention for validated triplets |
| `greylist_ipv4_prefix_bits` | `24` | Network prefix used to normalize IPv4 sources |
| `greylist_ipv6_prefix_bits` | `64` | Network prefix used to normalize IPv6 sources |
| `greylist_max_entries` | `1000000` | Durable triplet ceiling; capacity exhaustion fails open |
| `greylist_trigger` | `always` | `always` defers every unfamiliar triplet at RCPT; `score` defers only messages whose spam score reaches `antispam_greylist_threshold`, checked after DATA |
| `greylist_auto_whitelist_passes` | `5` | Passes within `greylist_pass_lifetime_days` after which a client network skips greylisting for every sender and recipient; `0` disables |
| `greylist_auto_whitelist_days` | `36` | Sliding period an auto-whitelisted client network stays whitelisted after its latest message |
| `greylist_skip_spf_pass` | `false` | Skip greylisting when SPF passes for the envelope sender's domain from the connecting address |
| `greylist_spf_pool_triplets` | `true` | When SPF passes, key the triplet on the sender's domain instead of the client network |

With `greylist_trigger = "score"`, known-good mail is never delayed: the
built-in spam engine scores the message first, and only a message scoring at
or above the greylist threshold (but below rejection) records its triplets and
receives `451 4.7.1`. A sender on any recipient's personal allow list is never
greylisted this way. The `score` trigger needs `antispam_enabled` and a
non-zero `antispam_greylist_threshold`; otherwise nothing is greylisted.

Auto-whitelisting, as in postgrey, counts each greylisting pass of a client
network (the same IPv4 and IPv6 prefixes as triplets). Once a network passes
`greylist_auto_whitelist_passes` times within one pass lifetime it is
whitelisted for all senders and recipients, and each further message extends
the whitelisting by `greylist_auto_whitelist_days`. Network counters are
hashed, durable, bounded by `greylist_max_entries`, and removed by the same
cleanup as triplets.

Large providers retry from different addresses in a sending pool, which would
restart greylisting for every attempt. With `greylist_spf_pool_triplets`, a
triplet whose envelope sender's domain passes SPF from the connecting address
is keyed on that domain instead of the client network, so a retry from any
address the domain authorizes matches. A pass earned under the network key
before the setting was enabled is kept. `greylist_skip_spf_pass` goes further
and does not greylist SPF-authenticated senders at all; it is off because
spammers can publish SPF for their own domains. The null sender is never
SPF-keyed.

Timing and capacity settings are validated and applied live as one
dependency group. `GET /api/v1/admin/greylisting` returns unit-labelled runtime settings,
durable counters, and active allow entries. Administrators can add or delete
CIDR, sender, or recipient bypasses and request bounded cleanup through the
same RBAC-, CSRF-, and audit-protected API.

### Content scanning

`local_domain_spoof_policy` defaults to `reject` for unauthenticated inbound
SMTP. A locally hosted envelope domain must have an exact SPF pass and a local
RFC 5322 From domain must have an aligned DMARC pass. `warn` accepts while
retaining a trusted `policy=fail` Authentication-Results method; `off` disables
the check. Authenticated submission is governed separately by owned-identity,
Send As, and Send on Behalf RBAC. Changes apply to the next SMTP session.

`helo_policy` validates the HELO/EHLO name announced on the inbound SMTP
listener: it must not be empty, an address literal, or `localhost`, and must be
fully qualified. `warn` (the default) accepts and logs the violation and adds
an `X-HELO-Status` header; `reject` answers `504` and the client may retry with
a valid name; `off` disables the check. The name is not required to match
reverse DNS. Authenticated submission is not subject to this policy. Changes
apply to the next session.

Content scanning is enabled globally and then assembled from any enabled
engine. Each engine has its own wall-clock limit, maximum accepted message
size, and outage behavior. `fail-open` records the error and continues,
`fail-closed` temporarily defers the complete SMTP transaction, and
`quarantine` accepts the message only into the durable system quarantine.

| TOML key | Default | Meaning |
|---|---:|---|
| `virus_scan_enabled` | `true` | Enable the shared content-scanning pipeline |
| `builtin_scanner_enabled` | `true` | Enable the built-in EICAR test-file detector (use ClamAV for malware signatures; risky attachment types are scored by the spam engine) |
| `builtin_scanner_timeout_seconds` | `5` | Built-in scanner deadline |
| `builtin_scanner_max_bytes` | `52428800` | Built-in scanner input ceiling |
| `builtin_scanner_failure_policy` | `fail-closed` | Built-in scanner outage action |
| `clamd_enabled` | `false` | Enable the ClamAV adapter |
| `clamd_socket` | `127.0.0.1:3310` | Clamd TCP address or `unix:/path/to/socket` |
| `clamd_timeout_seconds` | `30` | Clamd connection and scan deadline |
| `clamd_max_bytes` | `52428800` | Clamd input ceiling |
| `clamd_failure_policy` | `fail-closed` | Clamd outage action |
| `rspamd_enabled` | `false` | Enable the Rspamd adapter |
| `rspamd_endpoint` | `http://127.0.0.1:11333` | HTTP(S) `/checkv2` endpoint |
| `rspamd_password` | empty | Sensitive controller password, if required |
| `rspamd_timeout_seconds` | `15` | Rspamd request deadline |

The global switch cannot be enabled without at least one engine. Changes are
validated and activated live together in the `content-scanning` dependency
group; a scan already running finishes on the pipeline it started with. `GET /api/v1/admin/security/scanners` reports desired and
observed state without secrets; `POST /api/v1/admin/security/scanners/test`
runs a bounded harmless sample and is RBAC-, CSRF-, and audit-protected.
When Rspamd is active, `POST /api/v1/quarantine/{id}/train` accepts an explicit
`spam` or `ham` classification from an authorized administrator or mailbox
owner. It uses the configured input ceiling and a hard request deadline.
Training neither releases nor deletes the quarantine entry and does not mutate
private sender lists.

### Built-in spam scoring

Veksel scores every unauthenticated inbound SMTP message once per transaction
with a weighted rule engine. Each check emits a named symbol with a score, a
description, and options naming what matched (for example the listed IP or
link domain). Header and content heuristics, the SPF/DKIM/DMARC results the
SMTP boundary already evaluated, and DNS blocklists contribute symbols; the
total is compared to three thresholds:

| TOML key | Default | Meaning |
|---|---:|---|
| `antispam_enabled` | `true` | Score unauthenticated inbound mail |
| `antispam_junk_threshold` | `6` | Flag the message (`X-Spam-Flag: YES`) and file it in Junk; an account's own non-zero spam threshold takes precedence |
| `antispam_greylist_threshold` | `4` | Score at which `greylist_trigger = "score"` greylists; `0` disables |
| `antispam_reject_threshold` | `15` | Reject the transaction with `550 5.7.1`; `0` disables |
| `antispam_symbol_scores` | `[]` | `SYMBOL=score` overrides, such as `RBL_SPAMHAUS_PBL=0`; unknown symbols are rejected |
| `antispam_dnsbl_zones` | `[zen.spamhaus.org b.barracudacentral.org bl.spamcop.net psbl.surriel.com]` | Blocklists queried for the connecting IP (IPv4 reversed octets, IPv6 reversed nibbles) |
| `antispam_rhsbl_zones` | `[dbl.spamhaus.org]` | Blocklists queried for the registrable envelope, From, and HELO domains |
| `antispam_uribl_zones` | `[dbl.spamhaus.org multi.surbl.org multi.uribl.com]` | Blocklists queried for registrable domains linked in the body |
| `antispam_dns_resolver` | empty | IP address and optional port of the resolver used for blocklist lookups; empty uses the system resolver |
| `antispam_trusted_networks` | `[]` | IP addresses or CIDR prefixes never looked up in blocklists |
| `antispam_protected_brands` | `[]` | Brand names (`Contoso Bank`, at least three letters) or registrable domains (`paypal.com`) guarded against impersonation and lookalikes in addition to the hosted domains; up to 256 entries of 64 bytes |
| `antispam_url_shorteners` | bit.ly, bitly.com, tinyurl.com, t.co, goo.gl, ow.ly, is.gd, buff.ly, rebrand.ly, cutt.ly, shorturl.at, tiny.cc, rb.gy, t.ly, v.gd, s.id, lnkd.in, bl.ink, clck.ru, shorte.st, adf.ly, qrco.de | Link hosts scored as URL shorteners (host names, up to 512) |

Thresholds must keep greylist ≤ junk < reject. All settings are validated and
applied live in the `antispam` dependency group; a transaction finishes on the
engine it started with.

**Symbols and evidence.** The built-in symbols are `MISSING_FROM` (2),
`MISSING_SUBJECT` (1), `MISSING_MESSAGE_ID` (0.5), `MISSING_DATE` (0.5),
`CAPS_SUBJECT` (1.5), `SPAM_PHRASE` (3), `HTML_HEAVY` (1), `SALES_LANGUAGE` (1),
`FROM_DOMAIN_MISMATCH` (1), `SPF_FAIL` (3), `SPF_SOFTFAIL` (1.5),
`DKIM_INVALID` (2), `DKIM_MISSING` (0.5), `DMARC_FAIL` (2), and the zero-score
evidence symbols `DNS_LOOKUP_ERROR`, `USER_ALLOWLIST`, and `USER_BLOCKLIST`.

Header and MIME anomaly symbols (all overridable like any other):
`HDR_DATE_INVALID` (1), `HDR_DATE_FUTURE` (1.5, more than 24 hours ahead),
`HDR_DATE_PAST` (0.3, more than 7 days before receipt), `HDR_DATE_TZ` (0.5),
`HDR_MSGID_INVALID` (1), `HDR_MSGID_IP` (0.3), `HDR_MSGID_FORGED_LOCAL` (1.5,
a hosted Message-ID domain from an external sender without a DKIM or DMARC
pass), `HDR_RCVD_FORGED_LOCAL` (2, an older Received hop claiming delivery by
a hosted host name for an external sender; skipped for trusted networks),
`HDR_RCVD_ORDER` (0.8, Received dates more than a day out of order),
`HDR_FROM_MULTI` (1.5), `HDR_DUPLICATE` (1.5), `HDR_TO_UNDISCLOSED` (0.3),
`HDR_TO_FROM_SAME` (0.5), `HDR_RCPT_MANY` (0.8, more than 50 To/Cc addresses),
`HDR_SUBJ_ENCODED_ASCII` (1), `HDR_SUBJ_MIXED_CHARSET` (0.8), `HDR_SUBJ_NOISE`
(0.8, five or more repeated `!?$` or emoji), `HDR_FAKE_REPLY` (1, `Re:`
without In-Reply-To or References; `Fwd:` is exempt), `HDR_MAILER_SPAMWARE`
(2.5, a curated list of bulk-mailer X-Mailer/User-Agent names), `MIME_NO_BOUNDARY`
(2), `MIME_UNTERMINATED` (1), `MIME_NESTING_DEPTH` (1.5, deeper than five
multipart levels), `MIME_BAD_ENCODING` (1.5), `MIME_HTML_ONLY` (0.3),
`MIME_BAD_CHARSET` (0.8, invalid UTF-8 declared as UTF-8, or 8-bit
`us-ascii`), `MIME_BASE64_TEXT` (0.3, all-ASCII text in base64),
`HTML_HIDDEN_TEXT` (2, at least 200 letters hidden by inline `display:none`,
`visibility:hidden`, zero opacity or font size, the `hidden` attribute, or
text colored like its background; short preheaders do not trigger), and
`TEXT_ZERO_WIDTH` (2, three or more zero-width characters between ASCII
letters). Each carries the offending value or count as evidence. Mail from
authenticated submissions is never scored.
Delivered local mail carries `X-Spam-Score`, `X-Spam-Status`
(`Yes|No, score=… required=… tests=[…]`), `X-Spam-Symbols`
(`NAME(score), …`), and `X-Spam-Flag: YES` when flagged, so Sieve rules and
clients can act on them; peer-supplied copies of these fields are removed
first. The complete result, including options, also appears as the `antispam`
engine in the content-scan transcript retained by message trace and
quarantine inspection, and in the `X-Veksel-Content-Scan` summary.

**Blocklist zones.** A zone entry is a zone name, optionally followed by
space-separated rules: `CODE=SYMBOL:SCORE`, where `CODE` is an answer such as
`127.0.0.2`, a range `127.0.0.4-127.0.0.7`, a last-octet bitmask `&8`, or `*`
for any answer, and `CODE=!` marking the list's "query refused" answer. Known
lists need no rules: Spamhaus ZEN (`RBL_SPAMHAUS_SBL`, `_CSS`, `_XBL`, `_DROP`,
and `_PBL` with a small score; the Spamhaus DQS form `<key>.zen.dq.spamhaus.net`
is recognized), Barracuda, SpamCop, PSBL, Spamhaus DBL (`RHSBL_DBL_*` for
sender domains, `URIBL_DBL_*` for links), SURBL multi (`URIBL_SURBL_*`
bitmask), and URIBL multi (`URIBL_BLACK`, `URIBL_GREY`, `URIBL_RED`). An
unknown zone without rules scores any answer as `RBL_`, `RHSBL_`, or `URIBL_`
followed by the zone name. Answers in `127.255.255.0/24` (Spamhaus' typing,
public-resolver, and rate-limit errors), declared refusal answers such as
SURBL's and URIBL's `127.0.0.1`, and answers outside `127.0.0.0/8` (a resolver
rewriting NXDOMAIN) are never hits: they add `DNS_LOOKUP_ERROR` and degrade
the `antispam-dns` health component.

**Lookups.** No blocklist is queried for authenticated submission, loopback,
private, or link-local client addresses, `antispam_trusted_networks`, or
hosted domains. Link domains come from decoded text and HTML parts
(quoted-printable and base64), `href`/`src`/`action` attributes, bare domains,
email addresses, and defanged forms such as `hxxp://` and `example[.]com`; each
is reduced to its registrable domain with the public-suffix list, reserved
names are skipped, and at most 20 distinct domains are checked. Lookups run
concurrently with a 2-second per-query timeout inside a 5-second budget per
message; answers are cached (10 minutes listed, 5 minutes unlisted, bounded to
50,000 entries) and failures are never cached. Changing the resolver clears
the cache.

Most blocklists refuse queries relayed through large public resolvers, so a
server using one sees refusals instead of listings. Run a local recursive
caching resolver and point `antispam_dns_resolver` at it; see
[deployment](deployment.md#dns-resolver-for-spam-blocklists).

**Allow and block lists.** A sender on any recipient's personal allow list is
never rejected or greylisted; that recipient receives the message in the
Inbox with the symbols still recorded and `USER_ALLOWLIST` added. A sender on
the personal block list is filed in Junk with `USER_BLOCKLIST`. Accounts with
spam filtering off still receive the headers, judged against the server junk
threshold, but their mail is never moved.

`GET /api/v1/admin/security/antispam` reports the active thresholds, cache
size, and per-zone lookups, cache hits, listings, errors, refusals, and last
error. Prometheus exports `antispam_dns_lookups_total{kind,zone,outcome}`,
`antispam_actions_total{action}`, and the `antispam_score` histogram.

**Phishing and impersonation.** The engine also scores deception techniques.
Each symbol's options carry the offending value (truncated to 96 bytes), such
as `acmec0rp.com ~ acmecorp.com` or `paypal.com -> evil-site.net`, and every
score can be overridden with `antispam_symbol_scores`.

| Symbol | Score | Detects |
|---|---:|---|
| `PHISH_DISPLAY_ADDR` | 3 | The From display name contains an address or domain (`"support@paypal.com" <x@mailer.net>`) on another organizational domain; a sibling suffix of the same name (`Amazon.com` from `amazon.de`) is allowed |
| `PHISH_INTERNAL_NAME` | 2.5 | A sender outside the hosted domains uses a local user's multi-word display name (case, spacing, and homoglyphs ignored) or names a hosted domain (`AcmeCorp IT` for `acmecorp.com`) |
| `PHISH_LOOKALIKE_DOMAIN` | 4 | A From, Reply-To, or link domain imitates a hosted domain or protected brand: the same Unicode TR39-style skeleton (Cyrillic/Greek homoglyphs, `0`/`o`, `1`/`l`/`I`, `rn`/`m`, `vv`/`w`, accents), an edit distance of 1 (labels of 5+ characters) or 2 (9+), or the name as one hyphenated part (`paypal-secure.net`); the genuine domain and the same name under another suffix are not flagged |
| `PHISH_MIXED_SCRIPT` | 3 | An internationalized (punycode) domain label mixes scripts outside the TR39 highly restrictive combinations (Latin with Han/Kana, Han/Bopomofo, or Han/Hangul); single-script IDNs such as `münchen.de` or `яндекс.рф` pass |
| `PHISH_REPLYTO_MISMATCH` | 1.5 | Reply-To is on another organizational domain while From is a freemail provider or a hosted domain |
| `PHISH_HREF_MISMATCH` | 2.5 | An HTML link whose text is itself a URL or host name opens a different organizational domain or an IP address |
| `PHISH_URL_IP` | 2 | A link to an IP literal, including decimal, hexadecimal, and octal host forms |
| `PHISH_URL_SHORTENER` | 0.5 | A link to a host in `antispam_url_shorteners` |
| `PHISH_URL_SCRIPT` | 3 | An `href`, `action`, or `formaction` with a `javascript:`, `vbscript:`, or `data:` URI (whitespace inside the scheme is ignored; `data:` images in `src` are not flagged) |
| `PHISH_HTML_FORM` | 3 | The HTML body has a password input or a form posting to a domain other than the From domain |
| `SPAMTRAP_HIT` | 10 | The transaction was also addressed to a spamtrap (see [Spamtraps](#spamtraps)) |
| `PHISH_BRAND` | 3 | The display name or subject names a protected brand as a whole word (homoglyphs folded) unless DMARC passes for a From domain that is the brand's domain or carries its name |

Hosted domains and local display names come from the domain and account
directory through a cache refreshed every minute (a failed refresh keeps the
previous list and retries after 10 seconds), so new domains and renamed users
are protected without a restart. Hosted domain names are always protected:
in a display name they score `PHISH_INTERNAL_NAME`, and lookalikes of them
score `PHISH_LOOKALIKE_DOMAIN`; `PHISH_BRAND` covers `antispam_protected_brands`,
since colleagues and partners routinely mention the organization's own name
in subjects.

### Attachment policy

Veksel inspects the MIME parts of inbound mail for risky attachments, including
`message/rfc822` parts and ZIP archives one level deep. Inspection is bounded
(64 parts, depth 8, 32 MiB decoded per message, 8 MiB per attachment, 64
archive entries with 256 KiB read from each, a declared 1 GiB or 1000:1
expansion counts as a bomb) and never executes or fully expands content.

| TOML key | Default | Meaning |
|---|---:|---|
| `attachment_policy` | `quarantine` | Hard action for dangerous executables: `off` skips inspection, `score` only adds spam symbols, `quarantine` isolates the message for each recipient, `reject` answers `550 5.7.1` at the end of DATA |
| `attachment_blocked_extensions` | exe, scr, com, pif, bat, cmd, vbs, vbe, js, jse, wsf, wsh, wsc, hta, msi, msp, mst, lnk, cpl, jar, ps1, psm1, reg, iso, img, vhd, vhdx, apk, appx, msix, dll, sys, gadget, inf, scf, chm, ocx, application | Extensions treated as dangerous (letters and digits, up to 256 entries; a leading dot is ignored) |
| `attachment_check_submissions` | `false` | Also inspect authenticated submissions |

All three apply live in the `attachments` dependency group.

**Symbols.** Findings are scored by the built-in spam engine (so they need
`antispam_enabled` to count towards Junk or rejection) and appear in
`X-Spam-Symbols`, message trace, and quarantine transcripts, each with the
matching file names as options. Scores can be overridden with
`antispam_symbol_scores`.

| Symbol | Score | Detects | Hard policy |
|---|---:|---|---|
| `ATTACH_DANGEROUS_EXT` | 6 | A blocked extension, also on an entry inside a plain ZIP | yes |
| `ATTACH_DOUBLE_EXT` | 4 | A blocked extension behind a document or media extension (`invoice.pdf.exe`, `invoice.pdf .scr`) | yes |
| `ATTACH_TYPE_MISMATCH` | 4 | Content sniffing disagrees with the name: a PE, ELF, or Mach-O executable under a non-blocked name (hard), or a PDF, Office, or ZIP name with the wrong content | executables only |
| `ATTACH_MACRO` | 3 | Macro-enabled extensions (`docm`, `xlsm`, `pptm`, ...), a `vbaProject.bin` inside an OOXML ZIP, or a `_VBA_PROJECT` storage in an OLE2 file | no |
| `ATTACH_ENCRYPTED_ARCHIVE` | 3 | A ZIP with password-protected entries (names are still inspected) | no |
| `ATTACH_ARCHIVE_BOMB` | 3 | A ZIP declaring an implausible expanded size | no |
| `ATTACH_RTLO` | 6 | Right-to-left override, other bidirectional controls, zero-width or control characters in a file name; details show them as `<U+202E>` | no |
| `ATTACH_HTML_FORM` | 3 | An HTML attachment with a form, password field, or script | no |

Only the "hard" findings trigger `quarantine` or `reject`; everything else is
scored. The quarantine reason reads `Attachment policy: ATTACH_DANGEROUS_EXT
(invoice.pdf.exe)` and the policy's findings join the content-scan transcript
as the `attachments` engine. Office, Java, and packaged-app ZIPs (identified
by `[Content_Types].xml`, `META-INF/MANIFEST.MF`, or `mimetype`) are checked
for macros but their entries are not listed, since they legitimately contain
scripts. Nested archives, and tar, gzip, 7z, and RAR containers, are not
opened; their outer names are still checked. A personal allow list does not
bypass the hard policy.

**Authenticated submissions** are not inspected by default so users can send
legitimate files. With `attachment_check_submissions = true` they are
inspected and, because a submitted message has no local recipient to hold it,
both `quarantine` and `reject` answer `550 5.7.1` to the submitting client;
`score` has no effect on submissions (they are never spam scored).

#### Outbound sending limits and compromised accounts

Every authenticated submission — SMTP submission, webmail, JMAP, EWS, EAS,
and scheduled send — reaches the durable queue as one admission batch, and
that single choke point enforces per-account sending limits and watches for
compromised accounts. Mail generated by the server itself (bounces, vacation
replies, forwards, alerts) is not counted.

| TOML key | Default | Meaning |
|---|---:|---|
| `outbound_rate_limits` | messages_per_hour=500, recipients_per_hour=2000, recipients_per_day=10000 | Default per-account limits in `name=value` form; `0` or an absent name is unlimited |
| `outbound_compromise_threshold` | `80` | Compromise score at which an account is treated as compromised (0–1000); `0` disables detection |
| `outbound_hold_enabled` | `true` | Hold a compromised account's outbound mail for administrator review; when `false` only an alert is raised |

Limits use sliding one-hour and one-day windows. A submission that would
exceed one is refused as a whole and temporarily: SMTP answers
`451 4.7.0 sending limit reached: at most 2000 recipients per hour; try again
in 12 min`, webmail answers HTTP 429 with the same reason and a
`Retry-After` header, JMAP reports a `rateLimit` set error, and scheduled
send retries later. A limited account's first rejection per limit every ten
minutes is written to the audit log as `mail.send_limit`. Administrators
override the limits per account on the account's **Sending** tab (blank
inherits the server default, `0` is unlimited).

The compromise score sums independent signals over a sliding window:

| Signal | Moderate | Strong |
|---|---|---|
| `volume_spike` — recipients in the last hour against the account's hourly baseline over the past week | ≥ 50 and ≥ 5× baseline: 40 | ≥ 100 and ≥ 10× baseline: 60 |
| `new_recipient_domains` — recipient domains never used before, in the last hour | ≥ 10: 30 | ≥ 25: 50 (≥ 50 during the first day of a profile) |
| `bounce_rate` — permanent outbound delivery failures in the last day (at least 10 outcomes) | ≥ 30 %: 30 | ≥ 60 %: 50 |
| `login_spread` — successful protocol or web logins from distinct /24 (IPv4) or /48 (IPv6) networks in the last hour | ≥ 4: 30 | ≥ 8: 50 |
| `spam_content` — submissions scoring at or above `antispam_junk_threshold` with the outbound content rules (heuristics, phishing, MIME anomalies; no authentication or blocklist checks) | 1: 30 | ≥ 3: 50 |

When the score reaches the threshold the account is held: the hold is
stored on the account (and survives restarts), queued and new outbound mail
of the account is paused with the reason *Outbound mail held: suspected
account compromise*, one critical alert `Outbound mail held: <account>` is
raised through the health alert channels, and the account owner receives a
notification. The account's **Sending** tab shows the score, its signals,
current usage, and the held messages (envelope, subject, and size only);
**Release** lifts the hold and resumes the held mail, **Purge held mail**
cancels it, and **Reset credentials** replaces the password, signs out every
browser session, and revokes every application password in one action. A
release starts a fresh evaluation window, so old evidence cannot trip the
guard again. The held accounts are also listed by
`GET /api/v1/admin/outbound/holds`.

Counters and baselines are kept in memory and start empty after a restart;
until a profile is a day old, the new-domain signal needs 50 new domains in
an hour and the spike baseline is zero.

#### Statistical classifier

Every account has its own token-based (Bayesian) model that learns what that
user calls spam. It needs no external service.

| TOML key | Default | Meaning |
|---|---:|---|
| `antispam_bayes_enabled` | `true` | Train account models from Junk moves and score with them |
| `antispam_bayes_min_learns` | `200` | Spam messages and ham messages a model must each have learned before it scores (1–100000) |
| `antispam_bayes_autolearn` | `false` | Also learn from deliveries scored at confident extremes |
| `antispam_bayes_global` | `false` | Keep a shared server-wide model trained from every user's explicit actions |

The settings apply live in the `antispam-bayes` dependency group. The
classifier contributes only while built-in spam scoring is enabled.

**Training.** Moving or copying a message into Junk trains it as spam, and
moving or copying it out of Junk to any folder except Trash trains it as ham,
for the owner of the destination folder. The hook sits on the shared folder
space, so IMAP `MOVE`, JMAP, EWS, EAS, MCP, and web app moves (including
"Mark as junk" and "Not junk", which move to and from Junk) all train;
server-internal filing (SMTP delivery, Sieve, automation rules) never does.
IMAP `COPY` followed by expunge is a create in the target folder and does not
train. Each trained
message is recorded by a key derived from its Message-ID and body, so moving
it back untrains the old class before training the new one, and repeating an
action is idempotent. With auto-learning on, a delivery whose score without
classifier symbols is at least halfway from the junk to the reject threshold
(twice the junk threshold without one) trains spam, and one scoring at most 1
from an allow-listed sender whose DKIM or DMARC passed trains ham;
auto-learning never overrides an explicit action and never trains the shared
model.

**Scoring.** Tokens are lower-cased words of 3–24 characters from the decoded
subject (kept distinct), text, and HTML-visible bodies, plus the From domain,
mailer, relaying-host class, top-level content type, and linked registrable
domains, at most 1,000 distinct tokens per message. Probabilities use
Robinson's smoothing and Fisher's chi-squared combining over the 150 most
informative tokens. A probability of at least 0.99 adds `BAYES_SPAM` (5),
0.9–0.99 adds `BAYES_SPAM` at 60% of its score, at most 0.01 adds `BAYES_HAM`
(−3), and anything between adds the zero-score `BAYES_UNSURE`; the
`p=` and `model=` options show the probability and whether the account's own
(`user`) or the shared (`global`) model judged it. `antispam_symbol_scores`
overrides these scores like any other symbol. An account's own model scores
only that recipient's copy, after the transaction-level reject and greylist
decisions, so it moves mail between Inbox and Junk and appears in that
copy's headers and message-trace evidence. Only the shared model, when
enabled and trained, joins the transaction score and can therefore cause a
rejection; it also scores accounts whose own model is not ready yet.

**Storage and limits.** Account models live in the `bayes` namespace of the
account's own store, so they move, convert, and export with the
account; the shared model lives in the system store. Training runs on a
background queue (1,024 messages; overflow is dropped and counted). A model
keeps at most 500,000 tokens and 20,000 training records; when either cap is
exceeded a background pass prunes it to 90%, removing rare and stale tokens
first and the oldest records.

**Visibility.** `GET /api/v1/spam-classifier` returns the signed-in user's
trained spam and ham counts, token and record counts, the minimum, and
whether the model is ready; `DELETE` resets it. Administrators use
`GET`/`DELETE /api/v1/admin/users/{id}/spam-classifier`, see the settings,
the shared model, and training counters under `classifier` in
`GET /api/v1/admin/security/antispam`, and reset the shared model with
`DELETE /api/v1/admin/security/antispam/classifier`.

#### Sender reputation and auto-allowlist

| TOML key | Default | Meaning |
|---|---:|---|
| `antispam_auto_allowlist` | `true` | Score `KNOWN_CORRESPONDENT` on authenticated mail from addresses the recipient has written to |
| `antispam_reputation` | `true` | Learn decayed delivery outcomes per authenticated sending domain and sending network and score `REP_*` symbols |
| `antispam_reputation_min_samples` | `20` | Decayed observations a sender needs before it scores (1–100000); confidence reaches full strength at four times this |

The settings apply live in the `antispam-reputation` dependency group. Both
features contribute only while built-in spam scoring is enabled.

**Auto-allowlist.** Every durable submission (SMTP AUTH, webmail, JMAP, EWS,
EAS) already records its recipients in the account's `Recent recipients`
contacts folder; that folder is the correspondent list, so it is visible and
editable like any contacts and no second list exists. When mail arrives from
an address in it, the recipient's copy gets `KNOWN_CORRESPONDENT` (default
−3; `antispam_symbol_scores` overrides it), but only if the message
authenticated as that sender: DMARC pass, or an SPF or DKIM pass for the
From address's own organizational domain. A forged From, or a pass for an
unrelated domain, never benefits. The symbol is per recipient, after the
transaction-level reject and greylist decisions, and never applies when a
personal allow or block list already decided. Only individual addresses are
matched, not whole domains. It lowers the score only; malware, attachment,
and quarantine policies are unaffected.

**Reputation.** The engine keeps, server-wide, decayed counts per
authenticated sending domain (the organizational domain of the aligned
DMARC, DKIM, or SPF pass, else a passing DKIM `d=`) and per sending /24
(IPv4) or /48 (IPv6) network, never per address, user, or message. Each
scored inbound message from a public, untrusted client records one outcome:
accepted, junked (score at the Junk threshold), or rejected, judged without
reputation symbols so reputation never feeds on itself. Users' moves into
Junk and out of Junk (the same move observer that trains the classifier, and
independent of `antispam_bayes_enabled`) and owner releases of quarantined
messages count three times an automatic outcome. Counts halve every 30 days
and at most 50,000 senders are kept, least recently updated evicted first;
the state is saved every five minutes and on shutdown. Delivered messages
carry an `X-Veksel-Reputation` header naming the domain and network they were
judged under, which is how a later move finds them; a peer's copy is always
replaced.

Once a sender has `antispam_reputation_min_samples` decayed observations, at
least 60% against it adds `REP_DOMAIN_BAD` (3) or `REP_IP_BAD` (2), and at
most 10% against a domain adds `REP_DOMAIN_GOOD` (−2). Scores scale with
confidence (observations over four times the minimum) and, for bad senders,
with how far past 50% the bad share is; the symbol options show the samples
and bad share, and `antispam_symbol_scores` sets the full-strength scores.

**Visibility.** `GET /api/v1/admin/security/antispam/reputation?limit=25` lists the top
good and bad domains and networks that have enough samples, with decayed
counts per outcome, samples, and bad share; `DELETE` forgets every sender.

#### Fuzzy and bulk body detection

| TOML key | Default | Meaning |
|---|---:|---|
| `antispam_fuzzy` | `true` | Match bodies against locally learned spam and flag bulk mailings (`FUZZY_SPAM`, `BULK_SAME_BODY`, `BULK_NEWSLETTER`) |
| `antispam_fuzzy_threshold` | `80` | Percent body similarity that counts as a match (50–100) |
| `antispam_bulk_threshold` | `5` | Distinct unrelated senders of a near-identical body within one hour that make it bulk (2–60) |

The settings apply live in the `antispam-fuzzy` dependency group and
contribute only while built-in spam scoring is enabled.

**Fuzzy matching.** The decoded text and HTML body is normalized (lower-cased
words without URLs, addresses, numbers, whitespace, and quoted reply lines),
cut into four-word shingles, and sketched as a 64-slot MinHash, so changed
names, numbers, links, and spacing keep a body similar. Bodies under 20
words are not compared. The engine stores signatures of messages users move
into Junk (the same move observer as the classifier and reputation, counting
three times) and of deliveries scored at Junk or above without counting
fuzzy or bulk symbols (one). Weights halve every 14 days, at most 5,000
signatures are kept with the least recently updated evicted first, and the
state is saved every five minutes and on shutdown. A body at or above
`antispam_fuzzy_threshold` adds `FUZZY_SPAM` (default 4), scaled by the
similarity and by the stored weight (full strength at weight 2). Moving a
message out of Junk forgets every signature it matches.

**Bulk detection.** The engine remembers up to 2,000 recent bodies for one
hour, each with up to 64 distinct senders (authenticated or envelope domain
plus sending network), across all local recipients. Once more than
`antispam_bulk_threshold` senders have sent a body at least 90% alike it adds
`BULK_SAME_BODY` (default 2.5, scaled up to twice the threshold). Mail with a
passing DKIM signature and a `List-Unsubscribe` header gets the informational
`BULK_NEWSLETTER` (0) instead. Mail from private and trusted networks is
neither counted nor learned, and the bulk window is not persisted.

#### Spamtraps

| TOML key | Default | Meaning |
|---|---:|---|
| `antispam_spamtraps` | `[]` | Trap addresses (`trap@example.com`) or local parts (`trap`) that apply on every hosted domain, up to 1,000 |

A spamtrap is an address no legitimate sender knows, such as one only
published where harvesters scrape. The setting applies live; a list in which
an exact address is not on a hosted domain, or in which an address or a local
part on any hosted domain resolves to a user, alias, subaddress base, or
catch-all, is refused and the previous list stays. An identity created later
always wins over a trap.

Unauthenticated mail to a trap is accepted at RCPT like mail to any mailbox,
without greylisting, so the sender cannot tell it apart. A transaction
addressed only to traps is accepted whatever its spam score. Trap copies are
never delivered, queued, or bounced, and no DSN is ever sent for them. Once
the transaction is committed Veksel:

- learns the message as spam exactly like a user's Junk move: the sender's
  reputation domain and network get a weighted Junk outcome and the body
  becomes a fuzzy signature;
- strikes the sending IP with the `spamtrap` ban trigger (`ban_spamtrap_hits`);
- records a message trace entry (kind `spamtrap`, status `discarded`) for
  each trap.

When the same transaction also has real recipients, their copies get
`SPAMTRAP_HIT` (default 10, adjustable in `antispam_symbol_scores`), which
files them in Junk under the default threshold even while built-in scoring is
off. The symbol is added after the transaction-level reject and greylist
decisions, so a trap never causes a rejection the sender could observe.
Authenticated senders are never treated as hitting a trap.

### Synchronization credentials

Saving a source password is optional and is required for unattended schedules.
Stored passwords use versioned authenticated encryption envelopes and are
bound to the profile ID; connection/profile APIs never return them. Existing
plaintext credential records are encrypted automatically on their first read.
Administrators can inspect non-secret key status at
`GET /api/v1/admin/sync/credential-keys` and perform an audited, CSRF-protected
rewrap with `POST /api/v1/admin/sync/credential-keys/rotate`. Old key versions
remain available so interruption cannot strand a partly rotated credential
set. Key material is server-managed and is never exposed through either API.

### Quarantine lifecycle and digests

Quarantine entries use durable versioned item/byte accounting and separate
owner and expiry indexes. Status and quota-pressure views do not enumerate
message payloads. Startup and periodic cleanup are bounded, and capacity
exhaustion defers new quarantine admission instead of deleting an unexpired
entry. Administrators can inspect status, request cleanup, or rebuild derived
accounting and indexes from the Quarantine workspace.

Digests are opt-in per user and disabled globally by default. Enabling them
requires a public HTTPS origin; HTTP is accepted only for a loopback origin in
development. The scheduler persists a complete MIME snapshot before enqueue,
uses deterministic job identities and leased retries, resumes after restart,
and retains payload-free terminal evidence for the configured period. Signed
release and spam-confirmation links are scoped, expiring, single-purpose and
single-use. A GET renders confirmation only; the mutating action requires POST.

## Diagnostics

Veksel writes append-safe daily files named `veksel-YYYY-MM-DD.log` beneath the
system data directory's `logs` folder. `log_file_level` and
`log_console_level` are sink-wide minimums; `log_module_levels` contains the
live threshold for every registered runtime module. Valid levels are
`trace`, `debug`, `info`, `warn`, `error`, `fatal`, and `off`, which silences
the sink or module; `log_file_level = 'off'` opens no log file. Fatal records report
severity and never terminate the process from the logging library.

Administrators can filter, sort, and change every module threshold from
Operations. The same registry-driven control is also shown on the settings
page that owns each module, including every individual protocol page. Changes
use the managed configuration API, preserve unrelated TOML comments, take
effect without restart, and are retained in configuration history. Structured
fields and message text redact common credential, authorization, cookie,
token, password, secret, and URL-userinfo forms before either sink is written.

`pprof_listen` enables a separate, unauthenticated Go profiling listener and
is empty by default. Bind it only to a trusted interface. The administration
Operations view exposes queue state/actions, SMTP diagnostics, and folder-cache
hit, miss, eviction, entry, and byte counters.

| TOML key | Default | Meaning |
|---|---:|---|
| `metrics_token` | empty | Sensitive bearer token for Prometheus scrapes of `/metrics`; at least 16 characters |

`/metrics` answers `404` while `metrics_token` is empty and `401` unless the
request carries `Authorization: Bearer <metrics_token>`; the token is compared
in constant time. Administrators can always read the same counters through
`GET /api/v1/admin/metrics` (JSON) and `GET /api/v1/admin/metrics/prometheus`
(exposition format) and the administration Health view. A changed token applies
to the next scrape.

The JSON endpoint answers a bounded time window rather than every retained
sample: `window` (default `24h`; `15m`, `6h`, `7d`, or seconds; capped at the
seven-day retention), `end` (RFC 3339 or Unix seconds, default now), `points`
(default 288, at most 1000), and an optional metric `name`. Each series is
downsampled into equal steps (`step_seconds`) starting at `start`; a point's
`ts` is its step's start in Unix seconds and steps without samples are
omitted. Gauges report the step's last `value` and its `max`; counters and
histogram fields report the step's summed increase, so totals stay exact. Configure Prometheus with:

```yaml
scrape_configs:
  - job_name: veksel
    authorization:
      credentials: <metrics_token>
    static_configs:
      - targets: ['mail.example.com:8472']
```

The OpenAPI document (`/api/v1/swagger.json`) and its viewer (`/api/docs/`)
require a signed-in browser session or an administrator's `X-API-Key`.
Anonymous `/health` and `/api/v1/health` return only the status; build and
listener details are served to administrator API-key callers of
`/api/v1/health`.

HTTP(S) listeners bound request headers to 10 seconds and 64 KiB and close
keep-alive connections idle for 2 minutes. Each request receives a read and
write deadline: 2 minutes for ordinary requests and 1 hour for WebDAV, JMAP,
EWS, ActiveSync, MCP, and REST exports, imports, backups, attachments, file
uploads, and event streams. POP3 sessions are logged out after 10 minutes
without a command (RFC 1939), and POP3 listeners share the per-IP connection
rate limit used by IMAP and SMTP.

Secrets are marked sensitive in the schema, are not emitted by health or cache
diagnostic endpoints, and must never be logged.
